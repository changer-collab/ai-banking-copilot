### 2.7 飞书与多用户（P0）

目标顺序：

```
verify(签名 + timestamp±5min) → decrypt → parse(text / card.action)
  → resolve_user(binding) → 限流 → event_ledger.claim → _dispatcher_for(user_id).dispatch
```

必改：
1. 删全局 `dispatcher`，改 `_dispatcher_for(解析出的 user_id)`。
2. `resolve_user` 失败 → 绑定指引，**禁止** fallback。
3. `claim` 移到「验签 + 身份 + 限流」之后（现在验签通过就 claim，被 429 的事件已被消费，重投只拿到空回放）。
4. 补 `card.action.trigger` 回调（现在 `parse_event` 只认 `text`，飞书端无法确认执行 → `health` 不得把 adapter 报成可用）。
5. 验签补 timestamp / nonce。

**结论：组件语言一致，壳版本不一致。**

| 维度 | 徐思云 | 林晓研 | 高婧雯 | 尹辰（基线） |

| 结论 | rebase 后自动继承新壳；面板样式可直接并入 | 截图**不能作为最终验收图**，需在新壳上重截 | 同左 | — |

**结论一句话**：三个面板都与既有右栏卡片同款，**不需要改视觉**；需要统一的是版本链、CSS 落位、`apiFetch`、注册锚点（§2.2–§2.5）。

### 4.1 「前端示例」与当前分支的差异（决策）

`docs/2026-10-27/前端示例-网页端.html` / `-APP端.html` 是**静态结构稿**（68KB / 59KB，非空），主张 **7 视图信息架构**：左侧一级导航 → ① 首页入口 → ② 场景功能页（只有功能、没有聊天）→ ③ **对话独立页** → ④ 计划卡 → ⑤ 记录 → ⑥ 三态 → ⑦ 渠道健康。

当前实现是**单页三栏**：左栏（新建 / 历史 / 常用办理）+ 中间对话流 + 右栏处理详情。

**两处硬冲突**：
1. 示例把「对话」做成**独立一级页**；而 10-27 分工文档已拍板「聊天会话区放在场景功能面板下方，不作为独立一级页面或一级 Tab」。
2. 示例没有登录 / 个人中心 / 多用户 / 审计，只是 mock；按它重构会把这两天的隔离与会话历史推翻。

**建议（推荐 A）**
- **A. 以现实现为准，示例降为「结构参考」**：只吸收三件——① 首页场景入口卡（现有「常用办理」已接近）；② 三态（空 / 加载 / 失败）文案统一；③ 渠道健康做成右栏面板。**不做 7 视图重构**；在示例文件头部标注「对话独立页已废弃，以 `page.py` 为准」。
- B. 按示例重构 7 视图：工作量 ≥ 2 天，且与 10-27 拍板冲突，演示前不建议。
- C. 双轨（保留现页 + 新做示例页）：两套对话入口，演示时容易被问「到底哪个是产品」，不推荐。
