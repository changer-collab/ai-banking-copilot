## 1. 改动清单

### 1.1 `src/ai_banking_copilot/policy/pdp.py`

| 项 | 内容 |
|---|---|
| 改什么 | `OFFICIAL_RED_ACTIONS` 由 2 个动作扩为 5 个：新增 `card.set_limit`、`subscription.sign`、`transfer.request_collection`；docstring 补三条理由 |
| 为什么 | 用户裁决「都升红，有欺诈风险」。三者按金额档 / 可逆性只能落黄，不满足官方红色口径 |
| 影响谁 | 单节点裁决 `evaluate` → `_official_red_modifier`；计划级 `assess_plan` 逐节点复用同一函数；Web 计划卡 `_requires_for_level` 自动追加「强验证」；PEP `issue_write_grant` 对 RED 强制强验证证明 |
| 怎么回滚 | 把 `OFFICIAL_RED_ACTIONS` 还原为 `{"wealth.subscribe", "card.unlock"}` 两元素集合，同步还原下列测试期望即可（无数据结构变更、无迁移） |

三条理由（与三色表一致）：

- `card.set_limit`：调高卡片限额 = **解除既有风控上限**，且无金额参数（金额档不适用只会落黄）；
- `subscription.sign`：代扣签约 = **未来无限次扣款授权**，单笔小但敞口长期；
- `transfer.request_collection`：发起收款 = 向他人**索款**，电信诈骗典型施压手段。

## 2. 分派与内核查漏（结论：无需改动）

| 检查点 | 结论 | 依据 |
|---|---|---|
| PEP 写分派 | 无需改 | `Pep._dispatch_write` 按 `write_handlers` 注册表查表；三个动作的处理器分别由 `scenarios/cards.py`、`scenarios/subscriptions.py`、`scenarios/transfer.py` 自带并汇入组合根 |
| PEP 读分派 | 无需改 | 三个动作均非纯查询，不走读路径 |
| 内核 `assess_plan` | 无需改 | 逐节点经 `scenarios.authorization.node_policy_request` → `pdp.evaluate`，天然继承 `_official_red_modifier`；计划级 `evaluate_plan` 只看净效应与不可逆节点，不重复动作白名单 |
| Web 计划卡 | 无需改 | `plan_card._requires_for_level` 按 `Level` 映射，RED 自动带「强验证」提示；动作中文名表已含三者 |
| 会话执行 | 无需改 | `Session._execute` 对 RED 走 `issue_write_grant(verification_proof=...)`，与既有 `wealth.subscribe` / `card.unlock` 同一条已验证路径 |

一句话：**这三处升红只动了「一个常量集合」，其余链路全部按级别自动生效**——这正是当初把 `OFFICIAL_RED_ACTIONS` 设计成数据而非 if/elif 的原因。

## 5. 补能力：第 25 个动作 `password.change`（T4b）

赛题三级权限点名「密码修改」为红色，而收口后动作集里**没有**对应动作（空承诺）。故新增第 25 个动作：

| 层 | 改动 | 说明 |
|---|---|---|
| `tools/catalog.py` | 新增 `ToolSpec`（`RiskClass.SMALL_CHANGE` / `ActionKind.STATE` / `reversible=True`） | 只声明 `user_id` 控制槽 |
| `policy/pdp.py` | `OFFICIAL_RED_ACTIONS` 加 `password.change` | 无金额参数，按金额档只会落绿 ⇒ 必须白名单强制 ≥ 红 |
| `gateway/security_store.py` | **新建**独立表 `password_change_events`（`event_id/user_id/status/requested_on`） | 自带 DDL、幂等 init，**不并入** `store.py::SCHEMA_SQL` |
| `gateway/core_bank.py` | 新增写原语 `request_password_change`（幂等 / 单事务 / 确定性 id） | 只登记事件，状态 `pending_verification` |
| `gateway/facts.py` | 新增读方法 `password_change_event` + `_hash_by_pk` 分支 | 供 H1 出处校验回读 |
| `policy/pep.py` | `_read_hash` 加 `password_change_events` 分支 | 让 `record_ids` 真正通过出处校验 |
| `scenarios/cards.py` | `CARD_ACTIONS` + `_change_password_handler` + `WRITE_HANDLERS` | 仍属卡片域，**不新增第 7 个场景** |
| `web/plan_card.py` | 动作中文名「修改交易密码」+ 对象标签「本人交易密码」 | 级别驱动，RED 自动带确认 + 强验证 |
| `planning/llm.py` | 模板规则**最前**插「修改密码」 | 必须早于「转账」模板，否则「修改转账密码」被截走 |
| `eval/data/cases.json` | `password-change-red`（RED / 不拦截） | 92 → 93 条 |

**安全设计（答辩可用）**：`password.change` 的语义是「通过计划卡 + 强验证**发起**一次交易密码修改」——
**旧密码、新密码、密码摘要一律不入目录、不落库、不进模型上下文、不进审计**，真实改密由安全通道完成。
这比「把密码塞进对话链路」更安全，也是可对外讲的设计取舍。

**测试**：`tests/policy/test_pep.py::test_password_change_registers_event_without_password`（RED 确认 + 强验证 → 回读事件表校验）。

## 6. ⑥ 生日链路改为 `freeze → order → release`（T4c / B 案）

原链路只有一笔 `merchant.order`，「预算」只是文案，没有资金占用语义。B 案改为三节点：

| # | 节点 | 金额 | 说明 |
|---|---|---|---|
| 1 | `funds.freeze` | 1000.00 | 从账户可用余额划入预算 hold（`birthday:{user}:{year}:hold`） |
| 2 | `merchant.order` | 299.00 | 下单时从同一 hold **结算**（`settle_hold`），不是二次扣款 |
| 3 | `funds.release` | 701.00 | 释放剩余冻结额度 |

### 6.1 实现要点

- `scenarios/cross.py::birthday_plan`：手写三节点 DAG（`order1.depends_on=("freeze1",)`、`release1.depends_on=("freeze1","order1")`），三个节点共用 `budget_hold_id`，不再使用 `hold_id` 槽（避开 `_OBJECT_SLOTS` 的对象归属校验）。
- 账户选择：`accounts_of` 按 `account_id` 排序会先命中 `acc_current`，故**显式优先 `kind == "savings"`**，无储蓄账户时退回首个可覆盖预算的账户。
- `gateway/core_bank.py::place_merchant_order(hold_id=)`：结算 hold（递减、归零置 `status='released'`、不改 `amount_cents`），超额下单直接 `CoreBankError`。
- 判档双口径：计划卡展示与 `evaluate_plan` 用**净效应**（`funds.freeze/release` 中性，展示 299）；档位用**毛额**（`funds.freeze` 视同流出计入当日累计）。`eval/pipeline.py` 补 `_plan_daily_accumulated` 对齐同口径。
- 补偿：任一节点失败，撤销补偿对 `holds:` 前缀记录执行 `unfreeze_funds`，保证「冻结不悬空」。

### 6.2 展示数字的出处校验

`holds` 行在结算 / 解冻后被 UPDATE，历史哈希与当前行不再相等，而 `web_benchmark._verify_source` 只比对当前行。
因此 `eval/data/web_cases.json::web-cross-birthday` 的 `numbers` 改为三条规则：

| 展示数字 | 规则 | 不变式 |
|---|---|---|
| 299.00 | `merchant_orders.amount_cents` | 订单金额 |
| 1000.00 | `holds` 当前行 + `merchant_orders(status='placed')`，`operation: sum` | 冻结 = 结算 + 释放 |
| 701.00 | `holds WHERE status='released'` | 释放的是剩余额度 |

三者都能对**当前仍可哈希验证**的记录命中，同时保持真实账务不变式。

### 6.5 对外口径

> 生日场景不是「直接买花」，而是「先冻结 1000 元预算、按 299 元结算、把剩余 701 元原路释放」。
> 冻结期间额度不可被其他交易挪用；计划卡展示净流出 299，但判档按毛额 1000 计入当日累计——
> 因为冻结本身就是资金占用。含不可逆 `merchant.order`，整条计划判红、走强验证。
