# 代扣协议管理重构设计（P0–P2）

日期：2026-11-02
上游：用户截图与逐条问题清单（订阅页 + 对应 AI 问答）
状态：用户已确认方案 A，待实施

## 0. 一句话目标

把「订阅收藏夹」改回「代扣协议管理」：以银行卡侧的真实扣款授权为主对象，
关闭动作真实终止本行放款，并把签约时间、累计扣款、涨价、解约后对账全部讲清；
订阅识别降级为辅助筛选视图，页面与 AI 问答共用同一套事实口径。

## 1. 现状问题归因

| 现象 | 根因（代码位置） |
|---|---|
| 点「取消订阅」后按钮变「已取消」，但钱照扣 | `scenarios/subscriptions.py` 的能力边界写明「仅本地状态」；前端仍用成功态按钮，形成虚假成功反馈 |
| 业务对象是「订阅」，不是「代扣协议」 | `gateway/models.py` 的 `Subscription` 只有商户/金额/周期/下次扣款；没有协议编号、签约时间、协议类型、解约日期 |
| 「未来扣款」里挂着已过期日期 | `_next_charge()` 在无流水时直接返回登记值，不判断是否已过 `as_of`；`subscriptionTimelineHtml()` 也不过滤过去日期 |
| 「本月待扣」口径算不清 | `subscriptionSummaryHtml()` 只按「下次扣款日落在本月」求和，不区分已扣/未扣；年付不摊月但也没有说明它算哪个月 |
| 已取消仍强调 ¥25/月度 | `subscriptionCardHtml()` 对已取消项仍渲染金额与周期，没有解约日期与解约后对账 |
| 累计扣款缺失 | `SubscriptionInsight` 只有 `charge_count`，没有累计金额与首笔日期；`evidence` 只保留最近 6 笔 |
| 涨价只有一句话，没有对比 UI | `subscriptionAlertsHtml()` 只有一行文本；`price_change_12m_*` 没有生效日期与涨幅 |
| 扣款记录与单条协议不联动 | 「扣款记录」是底部独立按钮，跳到记录页全量列表，不能按协议查看 |
| 文案是工程术语 | 「取消口径」「数据边界」「业务日」「本地 / 商户边界」「识别说明（2）」直接暴露内部语言 |
| 账单线索与协议页各说各话 | 账单 `hidden-fee` / `recurring-subscription` 没有跳协议页的入口；`data-action="open-subscriptions"` 是无人触发的预留钩子 |

## 2. 业务模型：协议为主对象，订阅识别为辅助视图

### 2.1 派生 `DebitAgreement` 视图

不新增业务动作、不重写存储。新增场景层只读视图：

```python
@dataclass(frozen=True)
class DebitAgreement:
    agreement_id: str            # 由 subscription_id 派生，稳定
    agreement_no: str            # 展示编号 DD-{6 位派生哈希}（演示派生）
    agreement_type: str          # unionpay / netlink / collection_e / unknown
    agreement_type_label: str    # 银联代扣 / 网联代扣 / 代收e授权 / 类型未知
    merchant: str
    subscription_id: str | None  # 未匹配登记时为 None
    status: str                  # active / cancelled / suspected
    amount_cents: int
    cycle: str
    signed_on: date | None       # 最早一笔扣款日；无流水为 None
    cancelled_on: date | None    # subscriptions.cancelled_on
    last_charged_on: date | None
    next_charge_on: date | None  # 顺延后的推算值
    next_charge_is_estimate: bool
    next_charge_state: str       # scheduled / due / overdue / charged / cancelled
    overdue_days: int | None
    charge_count: int            # 全部期数，不只最近 6 笔
    charged_total_cents: int | None
    price_history: tuple[PricePoint, ...]
    price_change: PriceChange | None
    charges: tuple[AgreementCharge, ...]  # 最近 12 笔，供详情/扣款记录
    post_cancel_charges: tuple[AgreementCharge, ...]
    card_id: str | None
    card_tail: str | None
```

### 2.2 字段来源

| 字段 | 来源 |
|---|---|
| 协议编号 | `DD-` + `sha256(subscription_id)[:6]`，确定性派生；页脚标注「演示派生」 |
| 协议类型 | 借记卡 → 银联代扣；信用卡 → 网联代扣；未匹配登记 → 代收e授权（疑似）；无卡 → 类型未知 |
| 签约时间 | 该商户最早一笔流水的 `booked_on`；无流水如实显示「未知」 |
| 累计扣款 | 全部流水笔数与金额之和；无流水显示「数据不足」 |
| 最近扣款 | 最后一笔流水日期 |
| 下次扣款 | 有流水按周期推算；登记日期已过则按周期顺延；均标注「推算」 |
| 解约日期 | `subscriptions` 新增可空列 `cancelled_on`，由 `cancel_subscription` 写入业务日 |
| 解约后扣款 | `booked_on > cancelled_on` 的流水 |
| 涨价历史 | 按时间聚合连续不同金额，取新价生效日与相对涨幅 |

### 2.3 未匹配登记的商户

只来自流水的疑似商户（如「增值服务费」）：

- 状态标「疑似」；
- 明确提示「仅识别到流水，未匹配到本行代扣协议，可能是其他卡或其他渠道扣款」；
- 不提供「关闭扣款协议」按钮，只给商户自助取消指引；
- 账单隐藏费用深链打开该卡时，同样只做说明，不伪装成可关闭协议。

## 3. 金额与时间口径

### 3.1 三个数字，各自可解释

| 数字 | 定义 | 示例（as_of=2026-10-31） |
|---|---|---|
| 本月已扣 | 本月已记账的协议扣款合计（年付只在扣款当月计入） | 视频会员 ¥25 + 音乐会员 ¥12 = ¥37 |
| 本月待扣 | 从今天到月底、尚未到期的扣款 | 0（下一笔都在 11 月） |
| 未来 30 天预计 | 推算扣款日落在 `as_of` 起 30 天内；年付不摊月 | 视频 ¥25 + 音乐 ¥12 = ¥37 |

页面在每个数字下方给一句口径，不再用「年度订阅未折算到月」这类半句话。

### 3.2 时间状态翻转

`next_charge_state` 五态：

| 状态 | 判定 | 展示 |
|---|---|---|
| `charged` | 本周期已有流水 | 下次顺延到下一周期 |
| `scheduled` | `next_charge_on > as_of` | 正常排期 |
| `due` | `next_charge_on == as_of` | 今日到期 |
| `overdue` | 推算日已过且本周期无流水 | 琥珀提示「已过 N 天未见扣款，按周期顺延至 X（推算）」 |
| `cancelled` | `status=cancelled` | 不参与未来扣款与待扣合计 |

`_next_charge()` 规则：

1. 有流水且周期可判定：`last_charged_on + 周期`；
2. 若结果仍 `<= as_of`，按周期继续顺延到 `> as_of`，并置 `overdue_days`；
3. 无流水：取登记值；登记值已过 `as_of` 时按周期顺延，并标注「登记日期已过，按周期推算」；
4. 任何顺延结果都标 `next_charge_is_estimate=True`，不再冒充商户确认日。

### 3.3 未来扣款列表

- 只列 `next_charge_on > as_of` 且 `status=active` 的协议；
- 按日期升序，最多 6 条；
- 已扣的本期扣款不再出现在「未来扣款」，归入「本月已扣」；
- 逾期项单独置顶并标色，不混进正常排期。

## 4. 页面与交互

### 4.1 结构

```
[场景头] 代扣协议管理             [返回首页] [去对话办这一笔]
数据截至 2026-10-31 · 识别结果已同步
[一句话能力说明]
[本月已扣] [本月待扣] [未来 30 天预计]   [在签 3 项] [疑似待核对 0 项]
[扣款卡：全部 ▾]  [按协议 | 按商户 | 按周期]
[接下来要扣的（只列未扣）]
[在签协议]
  ├─ 协议卡：商户 + 类型 + 状态 / 金额·周期·下次 / 协议编号·签约·累计 / 最近扣款
  ├─ 涨价红条（如有）
  └─ [关闭扣款协议] [详情 · 扣款记录]
[已解约]
  ├─ 解约日期 / 最后一笔扣款 / 累计扣款
  └─ 解约后扣款对账（未发现 / 发现 N 笔 → 标红 + 申请追回）
[扣款记录] [刷新数据]
[这些商户是怎么识别出来的 ▾]
```

### 4.2 协议卡字段

卡片固定四段：

1. **身份**：商户名 + 协议类型 chip（银联代扣 / 网联代扣 / 代收e授权）+ 状态；
2. **金额与排期**：`¥12.00 / 月度 · 下次 2026-11-15（推算）`；
3. **协议事实**：`协议 DD-7F3A2C · 2025-01 签约 · 已扣 22 期 ¥222.00`；
4. **最近扣款**：`最近一次 2026-10-15`；
5. **涨价**（如有）：`¥10.00 → ¥12.00，自 2026-10 起（+20%）`，红色强调。

已解约卡不再展示「¥25/月度」为主信息，改为：

```
视频会员  已解约
解约日期 2026-10-31 · 最后一笔扣款 2026-10-18 ¥25.00
累计 22 期 ¥550.00
解约后扣款：未发现
```

「详情 · 扣款记录」弹层展示该协议最近 12 笔扣款（日期 / 金额 / 渠道 / 卡尾号 /
交易记录号），并提供「查看全部扣款记录」跳到记录页，不再让用户自己去全量列表里筛。

### 4.3 辅助视图

- `按协议`：默认，一条协议一张卡；
- `按商户`：同商户聚合，显示协议数、累计扣款、最近扣款；
- `按周期`：月度 / 年度两组；
- 视图切换只做前端分组，不改变服务端事实；
- 顶部卡筛选来自 `card_id / card_tail`，选中后出现「查看该卡全部代扣协议」。

## 5. 解约链路

### 5.1 页内二次确认

点「关闭扣款协议」打开弹窗：

- 标题：`关闭 {商户} 的扣款协议？`
- 协议事实：类型、编号、签约时间、累计 N 期 ¥X、最近扣款、下次扣款（推算）；
- 停扣影响：`关闭后这张卡不再向该商户放款；商户是否继续服务由商户决定。`
- 风险提示：`已产生的扣款不会自动退回；关闭后如仍被扣款，可在本页核对并发起追回申请。`
- 按钮：`先不关闭` / `关闭扣款协议`。

### 5.2 强验证

- `policy/pdp.py` 将 `subscription.cancel` 加入 `OFFICIAL_RED_ACTIONS`，理由：关闭扣款授权属于解除既有支付授权，与「解挂 / 调高限额」同类，单笔金额小不代表敞口小。
- 页内红色计划卡补非转账动作的验证面板：`获取验证码` → 演示码 → `提交验证码并关闭协议`。
- 对话内红色计划卡沿用现有 `verifyHtml`，只改按钮与提示文案。
- 所有验证码文案保留「演示验证码，非真实短信 / 人脸 / U 盾」。

### 5.3 执行与回执

`subscription.cancel` 写链路：

1. 校验 `(subscription_id, user_id)`；
2. 更新 `status='cancelled'`、`cancelled_on=业务日`；
3. 回执返回：解约日期、最后一笔扣款、解约后扣款检查结果、模拟短信回执。

回执卡结构：

```
关闭结果：已关闭本行扣款授权（商户未确认）
解约日期：2026-10-31
最后一笔扣款：2026-10-18 ¥25.00
解约后扣款：未发现
短信回执（演示）：【演示】您尾号 4471 的卡已关闭对视频会员的扣款协议…
说明：本行不再向该商户放款；商户侧订阅状态需到商户 App 关闭。
```

- 短信只做应用内回执，**不声称真实发送**；
- 如 `post_cancel_charges` 非空：标红 `解约后仍有 N 笔扣款`，给「申请追回」入口；
- 「申请追回」不新增业务动作，跳到对话并发起人工核对；AI 明确「需要人工核实，不能承诺退回」。

## 6. AI 问答与对话卡

### 6.1 `subscription.list`

回答协议事实，而不是订阅营销信息：

> 你名下这张卡有 3 个代扣协议：
> 音乐会员（银联代扣，协议 DD-7F3A2C，2025-01 签约，已扣 22 期 ¥222.00，最近 2026-10-15，下次 2026-11-15 预计 ¥12.00）；
> 视频会员（…）；云盘会员（年度，… 下次 2027-03-01）。
> 关闭后银行侧不再放款；商户是否继续服务由商户决定。

解约后回答：解约日期、最后一笔、解约后是否有扣款。

### 6.2 `subscription.cancel`

- 动作中文名：`关闭扣款协议`；
- 计划卡对象行：`{商户} · 协议 {编号} · 已扣 N 期 ¥X`；
- 计划卡行补：`关闭后银行卡侧不再放款；商户服务由商户决定`；
- 红色强验证；
- 回执与页面回执同源。

### 6.3 口述触发

`planning/llm.py` 模板规则新增：

- `关闭扣款协议`、`关闭代扣协议`、`解约代扣`、`关掉银行卡代扣` → `subscription.cancel`；
- 保留既有「取消订阅 / 退订 / 取消代扣 / 关掉自动续费」。

### 6.4 边界话术

替换 `web/session.py` 的商户取消话术：

> 本行能关闭的是银行卡侧的扣款授权；商户侧的订阅状态需要到商户 App 关闭，
> 本行拿不到商户的取消确认回执。

## 7. 账单线索闭环

- `hidden-fee`、`recurring-subscription` 线索增加「查看代扣协议」按钮；
- 跳转：`data-nav="scene" data-scene="subscriptions" data-sub-focus="{merchant_key}"`；
- 到达协议页后：
  - 命中已登记协议 → 滚动到对应卡片并打开详情；
  - 只命中疑似流水 → 顶部提示「未匹配到本行代扣协议，可能是其他卡或其他渠道扣款」；
- 文档与文案统一写「疑似隐藏费用」不再作为协议名，协议页一律用「代扣协议」。

- 受影响评测与测试：`eval/data/cases.json`、`heldout.json`、`heldout_v1.json`、`web_cases.json`、`evidence_dev_v1.json`、`tests/scenarios/test_subscriptions_regression.py`、`tests/web/test_subscription_*.py` 等，需静态同步为红色预期；执行结果由用户后续自行验收。

## 10. 非目标与风险

- 不新增业务动作、不接真实商户取消接口、不发送真实短信。
- 不改审计哈希、门禁判据与 PEP 三条硬约束。
- 风险 1：`subscription.cancel` 升红会改变多意图计划的整体等级（例如「转账 500 + 取消订阅」由黄变红），评测预期需同步。
- 风险 2：补音乐/云盘流水会改变账单分析的月度合计与趋势，这是有意让账单页与协议页同源；受影响的精确断言需同步更新。
- 风险 3：协议编号/类型为演示派生，必须在数据说明里标注，不得对外宣称真实银联/网联协议号。
