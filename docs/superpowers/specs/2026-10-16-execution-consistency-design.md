# 冲奖改进 spec：第一阶段执行一致性

日期：2026-10-16。代码基线：`53065f0`。

状态：方案 A 与本文已获用户批准，进入实施；用户明确允许修改受保护的 `contracts/plan.py`。其他受保护的算法、执行门判据、三条 PEP 硬约束及既有测试语义保持原约束。

## 1. 目标与路线

参赛目标是一等奖 / 金奖。技术改进按“可靠执行 → 可信评测 → 经实验证明的 AI 增益 → 演示与交付”推进。每个阶段单独验收；本 spec 只定义第一阶段的实施范围，后续阶段不提前扩建框架。

第一阶段要达到：用户确认的计划、实际执行的顺序、当时满足的授权条件、数据库产生的业务效果，可以逐项对应。继续使用 Python / FastAPI / SQLite、现有 PDP / PEP、动作注册表与服务端挑战，不引入分布式锁、消息队列或多智能体框架。

本阶段不承诺跨重启恢复会话、多节点计划整体 ACID、真实短信认证、审计抗抵赖或跨进程 JSONL 安全追加。保留现有逐节点提交与中断 / 补偿语义；同一 SQLite 数据库的业务授权与写入需要覆盖不同连接的竞争。

## 2. 已确认的问题

| 问题 | 当前行为及复现 | 修复后的行为 |
|---|---|---|
| 冻结信息不完整 | `PlanNode.canonical()` 不含节点 ID、依赖；反转依赖边后，执行顺序变化而哈希不变 | 节点身份、依赖及实际执行的确定顺序都被确认哈希冻结 |
| 过期裁决 | 两会话先分别提交 600 元、700 元，均黄卡；再确认时两笔均可完成，累计 1300 元未要求强验证 | 第二笔在写入的串行化点重新裁决，升红并停止，验证后才可继续 |
| 操作身份混同 | 两次独立提交相同的 200 元转账，复用“计划哈希前缀 + 节点 ID”，实际只记一笔 | 两次独立授权产生两笔；同一次执行重试只产生一笔 |
| 恢复跳过确认 | `submit → interrupt → resume` 可在没有确认记录时进入执行器 | 确认前恢复只回到待确认；确认后恢复必须验证原授权绑定 |
| 审计算法降级 | 有密钥实例按每行 `alg` 选择算法，服务启动可能接受攻击者重写的整条 SHA 链 | 服务启动拒绝 SHA 降级；旧链只经显式迁移进入严格通道 |

## 4. 冻结计划的完整语义

`cfhash(nodes)` 保持函数签名和 64 位 SHA-256 输出，改为带版本的规范载荷：

```python
{
    "version": 2,
    "execution_order": list(topological_order(Plan(plan_id="cfhash", nodes=nodes))),
    "nodes": [
        {
            "node_id": node.node_id,
            "action": node.action,
            "params": canonical_params,
            "intent": canonical_intent,
            "depends_on": sorted(node.depends_on),
        }
        for node in sorted(nodes, key=lambda node: node.node_id)
    ],
}
```

`cfhash` 先对临时 `Plan` 调用 `validate_plan`，再调用 `topological_order` 计算 `execution_order`；非法 DAG（重复 ID、重复依赖、未知依赖、缺锚点、循环）不得被哈希冻结。`topological_order` 保持现有“计划列表顺序决定并列节点”的 tie-break，因此改变实际执行顺序就改变哈希；只改变参数字典键序或同一依赖集合的声明顺序不改变哈希。修改节点 ID、依赖边、动作、参数、锚点都改变哈希。

`plan_id` 不作为业务内容摘要的一部分；独立操作由执行 ID 区分。`policy/gate.py` 仍使用原判据 `cfhash(plan.nodes) == frozen_hash`，不修改执行门算法。每次实际写入前复核计划哈希；确认后的可变参数不得绕过该检查。

升级后旧内存计划卡、挑战码失效，要求重新提交。当前没有持久待执行会话，不增加旧哈希兼容执行分支；历史审计保留原文，不重算、不覆盖。

## 5. 操作身份与确认状态

新增内部执行上下文，放在 policy / session 的实现模块，不扩展其他受保护 contracts：

```python
ExecutionContext(
    execution_id,       # 一次独立 submit 的随机唯一 ID
    frozen_hash,        # 完整 64 位内容摘要
    approved_level,    # 用户实际确认的授权级别下限
    strong_verified,   # 服务端成功消费挑战后记录，不能从“挑战不存在”推断
    completed_nodes,   # 此次执行已完成的节点与业务回执
)

node_key = f"{execution_id}:{frozen_hash}:{node_id}"
```

执行 ID 在一次新用户提交开始时生成。尚无已冻结计划的澄清续答沿用 ID；对已有计划修改内容或真正重新提交时生成新 ID 并使旧挑战失效。澄清使用内部续提交入口，不能直接调用会无条件生成新 ID 的公开 `submit`。确认重试、中断恢复均沿用当前 ID。确认记录同时绑定执行 ID、计划、完整哈希、获准级别、强验证结果。挑战除现有卡片 / 哈希 / TTL 外，也绑定本次执行 ID，避免相同计划间复用。

同一会话用 `RLock` 串行覆盖 `submit`、`clarify`、`confirm`、`request_verification`、`interrupt`、`resume`、`check_due`，防止并发确认、提交、恢复覆盖 pending / confirmation。数据库幂等仍是最后保障，不以会话锁替代业务事务。

既有到期预约与商户业务的稳定身份键继续由对应业务原语控制，不能被新会话执行 ID 覆盖。低层 CoreBank 目前不保证“任意同动作、同 key、不同参数”都报冲突；本阶段通过完整计划哈希绑定产品路径的普通节点键，不对低层 API 额外宣称该能力。

## 6. 最新风险复核与事务

### 6.1 同一套政策，两次使用

提交时的裁决用于展示计划卡；写入时的裁决用于决定能否产生副作用。两者复用现有 PDP 和动作注册表，不维护第二套金额 / 动作分级表。

最新裁决取以下结果的 `strictest`：原计划级下限、当前节点级裁决、全计划累计正向流出裁决、当前风险修饰。原计划级 Decision 只保留其级别和原因作为不可降低的下限，不能代替当前事实复核；当前级别超过 `approved_level` 时必须重新授权。原先要求的强验证不得因后续事实降低风险而自动取消。

计划累计口径：

```python
gross_plan_outflow = sum(本冻结计划所有 OUTFLOW 节点的声明金额)
external_daily_transfer = 当前日转账累计 - 本执行已入账且计入该累计的转账金额
projected_outflow = external_daily_transfer + gross_plan_outflow
effective_limit = min(官方阈值, 当前客户限额)
```

这里的“当日累计”沿用现有网关的已入账转账口径；计划内部叠加所有正向流出，不能称为跨业务全量日资金流出统计。金额、动作种类、收款人状态、限额与事实日期均来自现有可信网关 / 注册表。阈值比较规则沿用 PDP，边界值不自行放宽。

实际结算日与入账原语一致：普通转账取冻结的 `booked_on`，到期转账取 `executed_on`，其他流出取服务端基准日。涉及多个日期时，完整计划正向金额保守叠入各相关日的外部累计，逐日取更严裁决，展示最大预计累计；不能用基准日覆盖明确的入账日期。

赎回、解冻、取消订阅不能抵扣上述正向流出；现有净效应规则继续独立参与更严裁决。恢复时仅扣除本执行回执明确定位、确实计入当天累计的转账，不能扣其他会话或其他日期记录。完整计划正向金额保留，已完成的冻结 / 签约等未计入转账累计的动作也不会丢失或重复加总。客户限额可能随资产变动而收紧，此时如实升档。

### 6.2 原子边界

```text
Session：核对确认绑定、冻结哈希、会话熔断
  → PEP：保留白名单 / taint / 成员资格 / 绿色纯查询约束
  → 场景写 handler
  → CoreBank._run_once
      BEGIN IMMEDIATE
      业务身份 / 到期参数校验
      查幂等回执：已有则回放，不再制造副作用
      仅新写入检查当前收款人等业务状态
      读取本连接的最新风险事实 → PDP 复核 → 核对已获授权
      业务写入 + 幂等回执写入
      COMMIT（任一步失败则 ROLLBACK）
  → PEP：提交后回读出处、更新熔断、追加审计
```

事务唯一所有者是 CoreBank。给现有写原语增加结构化写前校验回调；所有 PEP 写路径都由 PEP 构造并强制传递回调，Web / IM / 到期派发提供完整执行上下文。仅 CoreBank 底层 TCB 调用可以省略回调；旧程序化 PEP 调用由 PEP 根据可信 Decision、计划及幂等键构造兼容上下文，仍执行相同最新风险复核。回调经 `WriteContext` 和 handler 明确传递，在 `_run_once` 中执行；不在 Web 加外层事务，不用全局临时回调变量，不让嵌套事务提前提交。

gateway 定义不依赖 policy / planning 的 `PreconditionResult` 和 `WritePreconditionError`。回调读取同一 SQLite 连接的事务事实快照，通过闭包绑定当前节点、冻结计划及 policy 层的 `ExecutionContext`，返回 `ALLOW`、`REAUTHORIZE(level, reasons, quota)`、`TAKEOVER(reason)` 或 `DENY(reason)`；gateway 不持有 policy 类型。`CoreBank` 只执行回调、识别结构化结果并在非 `ALLOW` 时回滚；PEP / Session 将结果映射为更新计划卡、清除挑战、回到待确认 / 接管 / 拒绝。SQL 与数值 / 实体构造留在 gateway，PDP 仍为纯函数。事务事实读取器只供受控校验使用，不把写连接交给 Web / LLM，也不把普通 `FactGateway` 的只读连接断言改成接受读写 Store。CoreBank 不反向导入 policy 或 planning。

所有产品写入口，包括 Web、IM 共用 Session、到期业务，必须经过相同写前校验。PEP 构造回调失败、完整上下文与计划不匹配时直接拒绝；兼容程序化入口以可信调用方提供的 Decision 为授权上限，不能把省略上下文视为关闭复核。直接调用 CoreBank 属于 TCB 内部原语，不是面向用户的授权入口；到期派发必须由受控执行器提供回调，不得以此作为绕过理由。

既有 `ReversalService` 是受控补偿例外，只处理本执行的回执以回补原扣款；剩余业务授权升档不妨碍已完成转账补偿。未核验的已提交回执先恢复核对再回退。旧 PEP 的可信 Decision 代表 TCB 提供的完整授权上限；外部请求不能注入此对象，Session 的强验证结果仅来自服务端挑战校验。

SQLite 的 `BEGIN IMMEDIATE` 负责不同连接的写串行化，实例 `RLock` 只负责本连接线程安全。事务内不调用通过另一写连接持久化的熔断动作，不写 JSONL。全局熔断状态在受控快照中读取并参与检查；事务退出后才持久化成功 / 失败计数，避免互锁。会话熔断在会话串行区检查。

### 6.3 风险变化与错误返回

若最新风险超过已确认条件，回调返回可识别的“需重新授权”结果，事务回滚。本次节点不产生资金 / 状态变更或成功回执。Session 更新卡片级别、原因和累计额度，回到待确认；若升级到红色，清除旧挑战并要求新的验证码；人工 / 拒绝按现有状态语义处理。

前端使用服务端返回的新卡片更新展示；既有 `/api/confirm` / `/api/verify/request` 继续使用，不增加第二个确认协议。计划内容未变时保留执行 ID 和已完成节点，卡片级别改变后旧卡确认请求失效。审批满足后，剩余节点仍逐次在事务中复核，不能依赖刚才展示时的快照。

风险复核不是预留额度：不同会话可以同时看到黄卡，但最多只有满足当前条件的写能通过。计划并非整笔事务；若前序节点已完成、后续节点升档，明确展示已完成部分，不能宣称整计划回滚。

业务已提交后，出处核验或 JSONL 追加失败，不能声称“资金未动”。停止后续执行并如实报告执行 / 审计状态；重试沿用原节点 key 取回执，不能重新扣款。本阶段不增加跨 SQLite 与 JSONL 的分布式事务或审计 outbox。

## 7. 中断与恢复

```text
待确认 → 中断 → 恢复 → 待确认（零业务写）
已确认 → 执行若干节点 → 中断 → 校验原授权 → 复核最新风险 → 执行剩余节点
任意恢复 → 缺确认 / ID 或哈希不符 → 不执行
任意写前 → 全局或本会话熔断 → 接管；纯查询继续遵守原语义
```

保留“确认前暂停”的交互能力，但恢复只能返回待确认。恢复执行必须存在匹配的确认记录和已满足的强验证状态，不能仅以 SessionState 判断。确认前暂停、红卡暂停、确认后暂停分别新增回归。

同一有效执行中消费过的验证码不要求每节点重复输入；仅恢复原已获准计划。新提交、换计划、授权升级均不能继承该强验证结果。本阶段只支持进程内会话恢复，不宣称重启后继续执行。

## 8. 审计严格入口与迁移

保留 `policy/audit.py` 的现有摘要 / 签名算法及低层 `verify_chain()` 兼容语义，不修改 `test_keyless_and_keyed_entries_coexist`。新增 `policy/audit_validation.py`，在组合根启动时叠加算法策略；密码学重算仍调用现有 `verify_chain()`，不复制一套 HMAC 算法。

服务严格规则：

1. 有密钥的空链或完整 HMAC 链通过。
2. 纯 SHA 链、未知算法、密钥错误、链损坏均拒绝启动。
3. SHA 只能是连续历史前缀；第一条 HMAC 必须是迁移事件，绑定此前 SHA 前缀的条数与链头。后续每条均须 HMAC。
4. 未提供密钥不能进入服务严格通道；历史混存链即使数学校验通过，也不自动获得服务信任。

提供离线迁移命令，要求停服务后显式输入旧条数与旧链头，核对纯 SHA 链、创建不覆盖原备份的副本，再用现有 `AuditLog.append()` 追加 HMAC 迁移事件。输入不匹配、链已混存 / 损坏、备份失败均退出且不追加。命令不能在服务启动时自动运行，也不能自动读取当前文件后把该结果当作外部可信锚。

迁移只表示运维确认接收这段历史，不能追溯证明旧 SHA 历史未被改写。默认同目录 key 的既有限制继续如实说明；本阶段解决算法降级，不宣称解决日志截断、密钥轮换或抗抵赖。

## 10. 验收用例与门禁

| 验收组 | 必须证明 |
|---|---|
| 冻结 | 改 ID / 依赖 / 实际执行顺序即哈希变化；仅改变不影响拓扑序的列表排列、字典键序或依赖集合声明顺序保持等价；冻结后篡改无业务写 |
| 独立操作 | 同一用户两次新提交 200 元，产生两个执行 ID、两笔记录、合计 400 元 |
| 幂等 | 同执行确认重试、并发确认与恢复不重复扣款；已有到期业务跨页面回放保持正确 |
| 计划累计 | 单计划 600 + 700 元直接升红；赎回 / 解冻 / 取消不能抵掉计划内流出 |
| 过期裁决 | 600 / 700 两会话先各获黄卡，再先后确认：第一笔完成，第二笔升红、零新增写，验证后只写一次 |
| 真并发 | 独立 Store / CoreBank 连接用同步屏障竞争同库，不能同时按旧黄卡完成；断言最终金额与交易数 |
| 续执行 | 本执行已完成转账不被重复累计，未完成节点仍参与总风险；其他会话的新支出可使恢复升档 |

| 熔断 | 确认后再熔断、恢复前再熔断均停止写；纯查询不被新逻辑锁死 |
| 原子性 | 写前拒绝或业务 body 异常时，账户 / 业务记录 / 幂等回执均无半成品 |
| 提交后失败 | 注入出处核验或审计追加失败：如实报告已提交结果，停止后续节点；沿原节点 key 恢复不重复写 |
| 程序化入口 | 直接经 PEP 的旧评测 / 内部调用即使省略新执行上下文，也必须进入最新风险复核，不能绕过累计与熔断 |

## 11. 逐步交付与后续阶段

第一阶段实施顺序：冻结契约 → 执行 ID 与确认 / 恢复绑定 → 事务内风险复核与累计口径 → 审计严格入口 / 迁移 → 服务联调与全量门禁。每一步保持可回归、可审查；实施计划在本文审阅通过后细化。

| 后续阶段 | 最小交付 | 进入下一阶段的条件 |
|---|---|---|
| 第二阶段：可信评测 | 扩现有 Web / HTTP / SQL 终态基准；固定通道标识、数据 / 代码摘要；严格真实模型模式禁止静默模板降级；同协议基线与消融 | 模板回归全过；真实模型逐例业务结果、安全副作用、延时和成本都有原始记录 |
| 第二阶段：独立盲测试点 | 建议冻结 40 例：24 合法、8 澄清、8 攻击；代码 / 提示词先冻结，独立出题与复核标签后冻结集合，结果揭盲前不调参；真实模型预设 3 次重复，失败留在分母 | 先登记成功标准再跑；重复次数不能充当独立样本数；复用过的集合转为回归，必须重新冻结新集合才能称盲测 |
| 第三阶段：AI 增益 | 先增强单 Planner，再比较 Reviewer 的纠错增益；业务事实与执行权仍留在可信确定层 | 对同一冻结集合证明完成率 / 澄清质量增益，并报告安全、成本、延迟变化；无增益则不引入多智能体 |
