# 官方五项安全机制补齐规格

起点：main / 70c5f2628ce6c405a6826e0b0defc6daeab5ff36。用户已批准设计及持续实施、PR 与合并。本规格只记录此次必要范围。

1. 幻觉防护：账单模型仅选择由事实支持的解释与建议标识，服务端渲染金额、实体与结论；任意自由文本、未知标识或事实错配均降级。不得只靠禁词。
2. 注入防御：保留控制槽、执行门与一次性 WriteGrant；写入授权字段来自验证后的 grant，不能信任可变执行上下文。
3. 审计：新事件记录统一 UTC 时间与关联身份；覆盖计划决策、确认、拒绝、挑战、工具执行和隔离执行。保持 HMAC / 哈希算法和启动校验不变；记录失败必须阻止需要授权的动作。
4. 安全锁定：验证码连续失败按用户持久化、跨会话/进程共享；伪造/重放/不匹配授权计入既有安全熔断。运维解锁先成功留痕再释放，审计失败维持锁定。
5. 沙箱：提供实际生成分析代码入口，只接收事实快照，结果经事实约束；在有资源限制及受限能力的独立进程运行，记录代码摘要、限制、耗时、退出和结果。平台不能建立要求的隔离时拒绝执行并如实显示。不得以不生成代码代替官方要求。

方案取舍：采用受限分析语言与独立受监控运行时，避免把任意 Python 解释器开放给模型；单纯正则/猴补丁不作为安全边界，重型外部集群不作为本地演示前置条件。实现须明确支持的语言子集和隔离层级。

验收：每项有实际 Web/业务入口及负例测试；ruff、严格 mypy、全量 pytest、确定性服务三项门禁通过；独立审查修复后 PR 合并。保护 docs/竞赛冲刺任务拆解-2026-10-20.md，不提交该文件。不修改 contracts、gate 判据、审计签名算法、PEP 三条硬约束及既有语义断言。

## 独立复核补充：PEP 熔断审计

PEP 或强验证失败计数通过连续授权失败使全局熔断从 `closed` 转为 `open` 时，必须在同一审计链追加一条 `breaker` 事件，至少记录 `CONSECUTIVE_AUTH_FAILURES`、`global`、`open`、触发动作/原因及可用的用户/会话/执行身份。熔断保持 `open` 时的后续拒绝不重复写转换事件；运维解锁后再次从 `closed` 转为 `open` 时必须再次留痕，即使历史触发项仍保存在熔断器中。熔断判据、计数器和审计签名算法保持不变；测试验证重复拒绝不制造新转换事件且解锁后的再触发有审计。

## 最终门禁修正

账单分析 DSL 生成器必须使用组合根创建并注入的同一份 `ModelConfig`，不得在请求执行时隐式读取宿主进程环境。这样 `build_deps(env=...)` 的确定性配置会覆盖规划、Reviewer 与分析代码生成，离线评测不会意外调用真实模型。生成/验证失败仍按现有安全语义拒绝输出事实。验收复用年度账单回归：`+17.65%` 必须有 18 条来源记录且哈希均通过。
