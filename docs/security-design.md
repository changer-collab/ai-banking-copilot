# 安全设计文档 · AI 银行副驾

> 覆盖官方必交文档之三：**安全设计文档**。术语口径：**借鉴**零信任原则（不信任模型自省），
> 不宣称等同金融零信任标准。PDP = 策略引擎（零模型参与）；PEP = 工具执行器（无裁决不执行）。

## 1. 威胁模型

| 威胁 | 攻击面 | 对策 |
|---|---|---|
| 事实幻觉 | LLM 编造账户 / 交易 / 数值 / 审查原因 | 事实零生成四分法 + TCB + 数值出处校验；Reviewer 只返回状态，用户文案由服务端模板产生 |
| 提示注入（直接 / 间接） | 备注、商户名、工具返回文本 | taint + 控制槽结构约束 + 执行门哈希 |
| 越权超标 | 多步组合绕过单步限额 | 计划级净效应 + 三色升档 + 执行门 |
| 时间旅行（TOCTOU） | 确认后篡改计划 | 计划级 `cfhash` + 节点级 `manifest_hash` |
| 重放 | 重复提交同一动作 | 幂等键 + 确定性回执 |
| 越权执行 | 模型直接调工具 | PEP 无裁决不执行；LLM 无执行接口 |
| 沙箱逃逸 | 分析计算访问网络 / 库 / 写盘或伪造出处 | 受限 DSL + 独立子进程 + 平台资源限制 + 来源校验 |
| 欺骗性措辞 | 诱导承诺收益 | 禁改语义清单 + 措辞白名单（只陈述事实） |
| 审查通道失配 | Planner 计划遗漏、额外动作或否定表达；模型编造澄清/拒绝文本 | 独立 Reviewer 绑定 `execution_id` / `cfhash`；严格通道只接受空解释字段，`clarify/reject/manual` 文案由服务端生成；异常时写动作转人工，纯查询保持原绿色语义 |
| 离线重发 | 浏览器缓存金融事实或排队重放写操作 | PWA 只缓存静态壳；`/api/*` network-only，离线禁用提交、确认、挑战和回退 |

## 2. 零信任三铁律

- **事实零生成**：数值（记录 / 算子）、实体（名册解析）、语义（规则）、措辞（禁改清单）四类各有确定性来源。
- **动作零越权**：动作只能来自白名单；PDP 裁决、PEP 执行；无裁决不执行。
- **输入零信任**：外部文本永不被解释为指令；控制槽只由确定性解析器填充。

## 3. 五道防线

1. **schema 层（类型系统）**：`Slot(CONTROL, Value(UNVERIFIED))` 构造即抛错（H3 落点）。
2. **策略层（PDP）**：官方三色 + 对象态机 + 单向升档 + fail-safe 合成。
3. **执行层（PEP）**：参数强校验 + taint 复核 + 执行门 + 幂等 + 执行后出处校验。
4. **通道层（审计 / 熔断）**：哈希链留痕 + 五类触发熔断（只加严不降级）。
5. **评测层（回归）**：序关系不变式 + 对抗样例库 + held-out + must-pass 外部锚。

## 4. 官方五项安全机制落点

| 机制 | 落点 |
|---|---|
| 权限分级机制 | `policy.pdp`（绿只含纯查询；日累计 1000 元为黄 / 红分界）+ `contracts.authorization` |
| 幻觉防护 | 事实零生成四分法 + `gateway.hashing` 出处校验 + `FactGateway.verify` |
| 注入防御 | `contracts.taint` 控制槽 + `tools.registry.validate_params` + `policy.gate` / `policy.pep` 执行门 |
| 操作审计 | `policy.audit`（追加式 JSONL + SHA-256 / HMAC 哈希链 + 决策链路字段） |
| 异常熔断 | `policy.breaker`（五类触发 + 只加严不降级） |
| 沙箱环境 | `gateway.sandbox`（受限分析 DSL 调用确定性算子；子进程无网络 / 禁库 / 禁写，并受时限、输入与输出预算约束） |

## 5. 信任边界与数据流

- **信任边界**：事实网关（TCB）以内为可信；LLM 侧与外部文本一律不可信。
- **数据流**：外部文本 → 数据槽（可承载任意来源）→ 仅展示；控制槽 ← 确定性解析器 / 交互层选定。
- **写路径唯一**：写只能经 `policy.pep` → `gateway.core_bank`；其它模块不得持有写连接。
- **主动洞察只读**：`InsightService` 每次扫描新建只读网关连接，来源记录和公式随结果返回；偏好与收件箱写入独立元数据库，不改变银行事实。

## 6. 残余风险与缓解

| 风险 | 缓解 |
|---|---|
| LLM 意图理解抖动 | 降级通道（模板 + 规则）；低置信度不猜，走澄清或安全拒绝 |
| 注入检测为标记词启发式 | 标记词仅作**升档载荷**；真正的防线是控制槽 schema 与执行门哈希 |
| 三色阈值被质疑过粗 | 以官方口径为准（H10）；增强层 L3/L4 与对象态机作补充 |
| 自建套件泛化效度 | held-out + must-pass 外部锚；**声明只证回归** |
| 沙箱与主进程同源 | 只解析受限分析 DSL，不执行任意 Python；独立子进程只读事实快照并回传带完整记录出处的派生值，禁止网络、写文件与 `sqlite3`。POSIX 使用 `rlimit`，Windows 使用 Job Object 与父进程 watchdog；这不是容器或独立身份隔离，生产化需独立容器。 |

## 7. 2026-11-02 增量与残余风险

- **动作集扩至 28**：`card.replace`（补卡）/ `card.adjust_credit_limit` / `card.set_cycle_limit` 均走同一 `policy.pdp` 三色裁决、同一 `policy.gate` 执行门与同一审计链；未新增授权路径。
- **卡片状态机**：临时冻结 `locked` 可逆、到期自动解挂；正式挂失 `lost` 为吸收态，只能补卡；`allowed_actions` 由服务端按状态算出，前端不得自行扩展按钮。
- **理财合规**：AI 只生成草案，申购 / 赎回统一进确认弹窗；四件套阅读、风险抄录、二次确认后才走 `/api/confirm`；65+ 与 R4+ 只做提示，未接真实双录。
- **代扣解约**：只终止本行侧授权，界面与回执如实写「商户侧以商户为准」；解约后扣款单列，不静默忽略。
- **账单与转账**：统一消费口径；转账记录只存账号后四位与演示开户行；未接真实清算与账户核验。
- **残余风险**：新增 R24–R28，完整清单见 [security-self-assessment.md](security-self-assessment.md) §二·补。
