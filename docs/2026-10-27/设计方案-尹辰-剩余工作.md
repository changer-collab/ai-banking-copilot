| 项 | v0.2 产品级做法 | v0.3 演示优先做法 | 为什么 |
|---|---|---|---|
| 身份层 | 预留 `IdentityProvider` 端口 + 预留 `core_bank` 改动 | **不抽象**，`web/auth.py` 一个具体 `AuthService`，凭证表与业务同库 | 端口抽象零演示价值，多一层就多一处出错 |
| CSRF | 双提交 token（前端要读、要回传） | **服务端校验 `Origin/Referer` + `SameSite=Lax` + 仅收 `application/json`** | 前端零改动，演示不会因 token 丢失白屏 |

| 阶段可见 | 轮询 300ms（曾评估 SSE） | **轮询 500ms + 拿到终态立即停**；失败退化为今天那句静态提示 | SSE 要改同步状态机+代理缓冲，台上一断流就整块空 |
| `/im` | 生产 404 + dev 开关 | **常开 + 必须登录**（不在导航暴露、页头写明"本地联调页"） | 开关忘了开就是现场事故；登录态反而能顺带演示多用户隔离 |

**保持不变（8 项）**：全站强制登录（空闲超时 60 分钟）、全量按用户持久化、个人中心、PlanCard 结构化（纯加法）、
生活事件记录、第二用户全场景 + ≥12 个月流水（改由启动/验收脚本注入）、审计轨迹可见化、共享模块只做加法。

## 0. 一句话结论

尹辰剩余 6 件事：**按登录用户隔离的场景/功能数据（登录 + 退出 + 个人中心）**、
**对话历史按用户落库并可在左栏点开**、生活事件面板（含"我的生活事件"小表）、
`/im` 本地联调页骨架、AI 问答**阶段可见**、验收记录与合并（+ D2 起 agent 改善一项）。

其中登录不是"换个 `user_id`"——每一类数据都必须在登录用户维度可存、可读、可隔离，这是本方案唯一会动
全局安全语义的改动（§3.1）。**对话历史**是本轮唯一新增的数据面（§3.8），因为快照里根本没有消息列表（见 §3.8.1）。

## 2. 设计原则

1. **数据按登录用户落库**：任何"场景/功能数据"（账户、卡、收款人、流水、理财、订阅、风评、洞察、
   会话快照、对话消息、生活事件、渠道绑定）都必须带 `user_id`，读写只用服务端解析出的 `user_id`。
2. **身份只信服务端**：不接受请求体里的 `user_id`。
3. **状态机只有一套**：面板、`/im`、个人中心、历史会话都复用 `Session.submit/clarify/confirm`，不新造对话链路。
4. **不伪装能力**：未接的（真实短信、真实 IM 平台、真实账号体系）显式标注为演示档；
   阶段必须是**真实执行阶段**，不允许纯前端假动画。
5. **演示可预期**：任何新能力都必须有"失败时退化成什么"的明确答案（见各节"降级路径"）。
6. **测试基线优先**：不破坏现有 1631 条；新能力另建测试文件。
7. **一人一分支**：全部改动进 `feat/yinchen`；共享文件（`app.py` / `page.py` / `app.js` / `session.py` /
   `session_manager.py` / `seed.py`）先发 5 行变更申请卡。

## 3. 模块设计

### 3.1 登录与「按用户隔离各场景数据」

#### 3.1.1 数据面现状（已核实）

| 存储 | 位置 | 是否已带 `user_id` |
|---|---|---|
| `users / accounts / payees / cards / transactions / wealth_holdings / subscriptions` | `gateway/store.py` | ✅ |
| `risk_assessments`（PK = `user_id`） | `gateway/risk_store.py` | ✅ |
| `merchant_orders`、`user_profiles`（PK = `user_id`） | `gateway/merchant_store.py` | ✅ |
| `session_snapshots`（PK = `(user_id, session_id)`） | `web/session_repository.py` | ✅ |
| `insight_preferences`、`insights`、`insight_scan_state` | `web/insights.py` | ✅ |
| `channel_identities` | `web/channels/identity.py` | ✅ |
| 新增 `conversation_messages`（§3.8） | 新文件 | **必须带 `user_id`** |
| 新增 `life_event_records`（§3.3） | 新文件 | **必须带 `user_id`** |

**结论**：多用户**结构上已就绪**，不是重写数据层。真正的缺口只有三处：

1. 种子只播一个用户（`gateway/seed.py` L20：`_USERS = ((DEMO_USER_ID, "陈明", "R3"),)`）；
2. 请求处理读的是常量 `deps.user_id`（`app.py` 13 处代码引用 + `_session_for`）；
3. 会话工厂**丢弃**了传入的 user（`app.py` L276–283 的 `factory=lambda _user, ...` 与 `restore`）。

**坑（必须写进实现清单）**：`account_id / card_id / payee_id / txn_id / subscription_id` 都是**全局主键**
（不是 `(id, user_id)` 复合键），第二份种子必须用不同前缀（`acc_b_*`、`txn_b_*`），
否则 `INSERT OR IGNORE` 会静默吞掉第二用户的行。

#### 3.1.2 请求级身份解析（三处切口）

**切口 A：会话工厂（最关键）**

```python
# web/app.py · build_session_manager
return SessionManager(
    deps.session_repository,
    factory=lambda user, session_id, lock: Session(
        replace(deps, user_id=user), session_id=session_id, shared_lock=lock,
    ),
    restore=lambda snapshot, lock: Session.restore(
        replace(deps, user_id=snapshot.user_id), snapshot, lock,
    ),
)
```

`Session` 内部所有读写（`accounts_of`、PEP 授权、审计、验证码计数、快照）都走 `self._deps.user_id`
（`session.py` 40+ 处），因此**只要把每用户 `AppDeps` 传进工厂**，场景与功能数据自动按人隔离，
无需改 Session 内部。`Session.restore` 有 `snapshot.user_id != deps.user_id` 校验（L480），
所以 restore 也必须按快照 user 重建 deps。

**切口 B：非会话路由（8 条）**

`/api/options`、`/api/insights`、`/api/insights/budget`、`/api/bills/analysis`、
`GET|POST /api/risk-assessment`、`/api/due`、`/api/me` 目前直接用 `deps.user_id`。改为显式依赖：

```python
def current_user(request: Request) -> str:
    """解析登录 cookie → user_id；未登录按 AIB_AUTH_MODE 决定 401。"""

@app.get("/api/options")
def options(user_id: str = Depends(current_user)) -> dict[str, object]: ...
```

每条路由"以谁的身份读"在签名上可见，测试可 `dependency_overrides`。

**切口 C：IM 本地通道**

`Dispatcher` 构造时固定 `server_user_id=deps.user_id`（`app.py` L335 / `dispatcher.py` L94–103、L168）。
`/im` 要登录态，就**按请求构造轻量 `Dispatcher(manager=..., server_user_id=current_user)`**，
不改 `dispatcher.py` 的签名（少一个共享文件冲突点）。

**统一口径**：`_session_for(session_id, user_id)` 显式接收 user；handler 不再直接引用 `deps.user_id`。

#### 3.1.3 账号、口令、会话（演示优先版）

- 新增 `web/auth.py`（**不引入 `IdentityProvider` 端口抽象**，就是一个具体类）：
  - `AuthService.login(username, password) -> LoginResult` / `logout(token)` / `resolve(token) -> str | None`。
  - 表（与业务同一个 SQLite）：
    - `auth_users(username PK, user_id UNIQUE, password_hash, salt, display_name, phone_tail, created_at, locked_until, failed_count)`
    - `auth_sessions(token_hash PK, user_id, issued_at, expires_at, revoked_at, user_agent, client_ip)`
  - 口令：stdlib `hashlib.scrypt`；库里只存 `hashlib.sha256(token)`，**不落明文**。
  - **登录失败策略（改动）**：连续 5 次 → 锁 **60 秒**；解锁后继续失败 → 每次锁定翻倍（120s / 240s / 上限 5 分钟）；
    成功即清零。演示现场手滑不会锁死整场。
- 预置 **2 个完整演示账号**（与第二份种子一一对应），口令写进验收记录，不进代码注释。
- Cookie：`aib_session=<token>; HttpOnly; SameSite=Lax; Path=/; Max-Age=3600`；空闲 60 分钟滑动续期（每次请求刷新 `expires_at`）。
- **CSRF（改动）**：不引入 token，改为
  1) `SameSite=Lax`；2) 所有写接口要求 `Content-Type: application/json`（浏览器跨站表单发不出该类型）；
  3) 校验 `Origin`（无 `Origin` 时回退 `Referer`）必须等于本站，否则 403 `cross_site_rejected`。
  前端零改动。
- 路由（`app.py`，共享文件 → 变更申请卡）：
  - `POST /api/auth/login`、`POST /api/auth/logout`、`GET /api/me`、`POST /api/auth/reverify`
- `AIB_AUTH_MODE`：`off`（单测基线用）/ `demo`（未登录一律 401 + 登录页）。
  **部署与验收脚本显式设 `demo`**；`off` 只允许测试进程使用。

#### 3.1.5 退出与会话失效

- `POST /api/auth/logout`：撤销 token（`auth_sessions.revoked_at`）→ `manager.drop(user_id)`（清内存会话）→ 清 cookie。
- **快照保留**：同用户重新登录后仍能从左栏点开历史会话（这是 §3.8 的特性，不是漏洞）；
  换账号登录读不到（`user_id` 不同）。验收记录里写明这条口径。
- 打开历史里 `awaiting_confirm` 的会话时，计划卡若已超过 `expires_at`，前端显示"计划已失效"、
  `/api/confirm` 由服务端拒绝（现有逻辑已校验，不新增）。

#### 3.1.6 敏感操作二次验证

- 交易类（转账/申购/挂失等）：**复用**现有 `/api/verify/request` + `/api/confirm`，不新增旁路。
- 账号类（解绑渠道、删除历史会话）：用 `/api/auth/reverify` 的短时票据（5 分钟）。
- 改密：个人中心**只放入口跳计划卡**（`password.change` 已在 `core_bank`），不提供直改旁路。

```sql
    user_id      TEXT NOT NULL,
    session_id   TEXT NOT NULL,
    event_id     TEXT NOT NULL,          -- L1..L7 / C1..C3
    event_name   TEXT NOT NULL,
    amount_cents INTEGER,               -- 仅表单参数；自然语言触发为 NULL
    status       TEXT NOT NULL,          -- planned / executed / rejected / failed
    created_at   TEXT NOT NULL,
    updated_at   TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_life_event_user ON life_event_records(user_id, created_at DESC);
```

- **类型来源**：服务端对提交话术调用现有 `detect_life_event` / `detect_life_combo`（与规划同一检测器），
  命中才记录——不新增客户端字段。
- **写入时机**：`/api/submit` 返回计划卡（`awaiting_confirm` 且有 card）写 `planned`；
  `/api/confirm` 成功置 `executed`；`/api/reject` 置 `rejected`；执行失败置 `failed`。
- **金额口径**：只取面板表单的结构化参数；自然语言触发显示「—」，不从计划卡文本猜金额。

### 3.5 生成阶段可见（Q5）

**目标**：AI 回答生成前，前端动态显示当前阶段；答案落地后立即收起，不留占位。
**诚实前提**：阶段必须是服务端真实执行到的步骤，不允许纯前端假动画/假百分比。

| 阶段 key | 前端文案 | 代码位置（`Session._submit` L642–710） |
|---|---|---|
| `guard` | 正在做安全检查 | 注入检测 + `_guard_utterance` + `_invalid_selection` |
| `understand` | 正在理解您的需求 | `_assemble_intents`（通常最慢） |
| `plan` | 正在匹配场景并组装计划 | `select_handler` + `run_scenario` |
| `review` | 正在做权限裁决并生成计划卡 | `_after_outcome`（PDP + 审计 + 计划卡） |
| `done` | 已完成 | 任意出口（含澄清/拒绝的提前返回） |

**实现（不动同步契约）**

1. `Session.submit(..., on_stage: Callable[[str], None] | None = None)`，`clarify` 同签名；
   `_submit` 在 4 个边界回调，`finally` 发 `done`。`on_stage=None` → 零行为变化，现有测试不受影响。
2. 进程内 `ProgressRegistry`：key `(user_id, session_id, request_id)`，字段 `stage / updated_at / finished`，
   锁保护、TTL 120s、只允许同一 `user_id` 查询。
3. `/api/submit` 请求体新增**可选** `request_id`；带则注册进度并在响应后标 `finished`，不带走旧路径。
4. `GET /api/progress?session_id=&request_id=` → `{stage, stages, finished, updated_at}`。
5. 前端 `post()`：生成 `request_id` → 启动 **500ms 轮询**（不叠加：同一时刻只有一个轮询）→ 渲染步进器
   （已完成打勾、当前高亮、无百分比）→ `fetch` 返回后停轮询、**立即收起**，再渲染回答。
6. `clarify` 复用同一套。

**与状态机锁**：`Session` 方法被 `_serialized` 串行化；进度查询只读 `ProgressRegistry`，不碰 `Session`。
`/api/submit` 是同步 `def`，FastAPI 在线程池执行，轮询可并发进入。

**降级路径**：轮询接口报错 → 不显示步进器，退回今天的静态"正在请求…"；答案照常渲染。
模板通道 <500ms 跑完 → 步进器闪一下或不可见，**不伪造**。

**D9 决定取 A**：允许"最短展示 400ms"（阶段真实，只延迟收起）——演示时保证能看到；
这是 UI 停留，不是伪造阶段，验收记录里注明。

### 3.8 对话历史（按用户落库 + 左栏可点开）— 本轮新增

#### 3.8.1 为什么不能只靠快照（已核实）

`Session._SNAPSHOT_FIELDS`（`session.py` L386–393）是**白名单**：`message / pending / confirmation / …`，
**没有消息列表**；`restore` 还强校验 `set(payload) == {*_SNAPSHOT_FIELDS, "session_breaker"}`
（L483–484）。所以：

- 扩快照 = 改共享文件 `session.py` + 改 codec + 版本号 + 旧快照兼容，风险高；
- **独立消息表与快照解耦**，既可列历史，也不动状态机。

#### 3.8.2 表与接口

新文件 `web/conversation_store.py`（与业务同库）：

```sql
CREATE TABLE IF NOT EXISTS conversation_messages (
    message_id  TEXT PRIMARY KEY,
    user_id     TEXT NOT NULL,
    session_id  TEXT NOT NULL,
    role        TEXT NOT NULL,          -- user / assistant
    kind        TEXT NOT NULL,          -- text / plan_card / receipt / error
    text        TEXT NOT NULL,
    payload_json TEXT,                  -- 计划卡结构化字段（§3.9）；text 类型为 NULL
    created_at  TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_conv_user ON conversation_messages(user_id, session_id, created_at);
```

接口：

| 方法 | 路径 | 行为 |
|---|---|---|
| `GET` | `/api/conversations` | 该 user 的会话摘要列表：`session_id / title（首条 user 消息前 20 字）/ last_active_at / state / message_count`，按 `last_active_at DESC` 取 50 条 |
| `GET` | `/api/conversations/{session_id}` | 该 user 该会话的消息数组 + `state` + 未过期的计划卡（`requires` 照旧） |
| `DELETE` | `/api/conversations/{session_id}` | 删消息 + 删快照 + `manager.drop(user_id)`；需 `reverify` 票据 |

**隔离**：三个接口都强制 `WHERE user_id = current_user`；路径里的 `session_id` 不构成授权。

#### 3.8.3 写入点（只加在 `app.py`，不进 `Session` 内部）

- `/api/submit` 成功后：写 1 条 `user/text`（原始话术）+ 1 条 `assistant`（`kind` 按响应决定：
  有卡 → `plan_card`；澄清 → `text`；拒绝 → `error`）。
- `/api/confirm`、`/api/reject`、`/api/reverse` 成功后：追加 1 条 `assistant/receipt`。
- 写失败**不影响主流程**：捕获异常、记 warning、继续返回业务响应（历史是旁路，不能阻断交易）。

#### 3.8.4 前端

- 左栏 `#conversation-list` 改为**登录后首屏拉 `/api/conversations`** 渲染，去掉"临时"徽标。
- 点击历史项：拉 `/api/conversations/{id}` 渲染消息 → 把 `SESSION_ID` 切成该 `session_id`
  → 后续交互由 `SessionManager` 从快照 restore（`awaiting_confirm` 的卡若过期则置灰）。
- 「新建对话」保持现有逻辑（生成新 `session_id`，不写库，直到首次提交）。
- 单条删除：长按/悬浮菜单 → `reverify` → `DELETE` → 从列表移除。
- 资源版本递增：`app.js?v=16`、`workspace.css?v=6`。

### 3.9 PlanCard 结构化（纯加法，演示与无障碍都需要）

现状 `PlanCard` 只有 `lines: tuple[str, ...]`（`plan_card.py` L75–86），`_card_payload`（`app.py` L944–955）
输出 `{card_id, frozen_hash, level, lines, requires, expires_at, balance_trace}`。

改动：

- `PlanCard` 增字段 `summary: tuple[PlanLine, ...]`（`PlanLine = (label, value, emphasis)`），**`lines` 原样保留**；

- 生活事件小表金额、`/im` 计划卡摘要、屏幕阅读器朗读都读 `summary`，不再从文本抠。

**风险控制**：纯增量字段，旧快照/旧前端回落 `lines`，不破坏现有断言。

## 4. 验收标准（可判定）

1. **跨用户隔离**：A 登录 → `/api/options` 只含 A 的账户/卡/收款人；B 登录看到 B 的；
   用 A 的 `session_id` + B 的 cookie 请求 `/api/session`，**响应不含 A 的 card_id / 计划卡 / 消息**。
2. **未登录**：`AIB_AUTH_MODE=demo` 下访问 `/` → 登录页；错口令 5 次锁 60 秒（解锁后可再试）；
   Cookie 为 HttpOnly + SameSite=Lax；跨站 `Origin` 的写请求 → 403。
3. **退出**：退出后旧 cookie 请求 `/api/session` → 401；同用户重新登录能从左栏打开此前会话；
   换 B 登录看不到 A 的会话。
4. **对话历史**：A 发起 3 段会话 → 列表 3 条、标题为首句、时间倒序；点开恢复消息与状态；
   删除一条后列表消失且该 `session_id` 直接访问 404。
5. **生活事件面板**：七卡可点；L1 填参数 → 计划卡（`summary` 有金额）→ 确认 → 执行成功；
   「我的生活事件」出现一行，类型/金额/状态正确，**只出现在发起用户的表里**。
6. **`/im` 骨架**：登录后可用；输入框 + 气泡 + 计划卡（`summary`）+ 确认按钮跑通"文本进 → 计划卡 → 确认 → 回执"；
   页头写"本地联调页"；零外链。
7. **阶段可见**：LLM 通道下能看到 ≥2 个真实阶段；回答出现后步进器立即收起、无残留；
   轮询失败时退回静态提示且回答照常渲染。
8. `ruff check .` / `mypy src` / `pytest -q` 全绿（**实测**）。
9. 资源版本递增：`app.js?v=16`、`app.css?v=7`、`workspace.css?v=6`（如动样式）、PWA 壳按现有约定。
