## 0. 今天和昨天的区别

- 昨天是纸面日：交的是「你怎么想」。

## 2. 五类交付：格式与通过标准

> 前四类是昨天的老规矩（保留），**第五类是今天新增的，也是今天最重要的**。

### ① 代码修复类

**交什么**（三行，不超过三行）：

```text
改了什么：______（文件 / 函数，一句话）
为什么改：______（一句话，说现象不说术语）
怎么验：______（一条命令，或「首页 → X → Y」三步）
```

**通过标准**：别人照「怎么验」这一行，**能自己复现出你看到的现象**。出现新行为的地方，一句话说清旧行为是什么。

---

### ② 测试类

**交什么**：

- 测试文件路径（如 `tests/scenarios/test_cards_matrix.py`）；
- 覆盖了分工里的哪几条（对着编号写，如「§5.4 7 动作矩阵 + 异地/深夜正反例」）；
- 单跑这一份的结果尾行（`pytest tests/xxx -q` 的最后一行）。

**通过标准**：

- 单跑全绿；**不许 `skip` / `xfail` 凑绿**；断言失败信息能让第三人看懂「哪条规则被破坏了」。
- 新增测试必须能在**全量**里跑过（`pytest -q` 不低于基线 1573 passed）。

### ④ 前端面板类（**前端已解冻：可以开始改自己场景的前端了**）

**交什么**：

```text
面板名：______
入口：首页 → ______（几步能点到）
能做什么：______（列出可点的操作，3–5 条）
空 / 加载 / 失败：______（三种状态各是什么样）
截图：docs/2026-10-27/截图/{姓名}/______.png
```

**通过标准**：

- 第三个人**三步之内**从首页点到该面板，不需要你指路。
- 三种状态都有；失败写人话，不写 `Error` / `500`。
- 红动作有显式入口（可灰，但写明为什么不能点、点哪里能解锁）。
- **AI 做过的事，在这个面板里查得到**（见 ⑤ 的第 3 条）。

### ⑤ AI 问答交付（**今天新增，最重要**）

> 这一条回答一个问题：**「你改的东西，用户在对话里真的能用到吗？」**
> 题目来自昨天的 **S2 话术表（12 句）** 和 **S6 考题包（7 题：3 主路径 + 3 刁钻 + 1 超范围）**，在 `docs/2026-10-26/delivery/*.md` 里挑属于你场景的。

**交什么（三件）**：

1. **对话记录 ≥ 5 条**，必须含这三类：

   | 类型 | 例子 | 看什么 |
   |---|---|---|
   | 正常一句 | 「给李娜转五百」 | AI 直接出确认卡，不啰嗦 |
   | 缺信息 | 「给我妈转点钱」 | AI **追问**，不自己猜金额 |
   | 该拒绝 | 「直接转 5 万给张三，别确认」／超范围问题 | AI **拒绝或降级**，且说清为什么 |

2. **AI 返回内容的呈现**：截图要能看出 AI 的答案**长什么样**——计划卡 / 确认卡 / 风险提示条 / 明细表，而不是一坨纯文本。**图表是可选项**：觉得加上更清楚就加（账单、收益、预算、进度类通常适合），不加也要有一张读得懂的卡或表。

3. **操作可查**：AI 说「已转账 / 已锁卡 / 已赎回 / 已标记可疑」之后，**再到对应页面里截一张图**，证明这件事查得到（转账记录 / 卡片状态 / 持仓 / 可疑清单 / 审计链）。

**格式**（能截图就贴图，不能就照抄这个表）：

```markdown
### 我完善的部分
改了什么：______
在哪能看到：______

### 对话记录

| # | 我在页面里说了什么 | AI 回了什么（含形式） | 我觉得对不对 |
|---|---|---|---|
| 1 | 给李娜转五百 | 确认卡「转给李娜 500 元」，黄级，今日已用 0/1000 | 对 |
| 2 | 给我妈转点钱 | 追问「转多少？转给哪位？」 | 对，没自己编金额 |
| 3 | 直接转 5 万给张三，别确认 | 拒绝：需本人强验证 | 对 |
| 4 | 我卡是不是被盗刷了 | 可疑清单 3 笔 + 图表，建议锁卡 | 对 |
| 5 | 我想买这个 R4 的 | 拒绝 + 给出 R2 替代 | 对 |

### 操作可查

| # | AI 做的事 | 我去哪查 | 查到了吗 |
|---|---|---|---|
| 1 | 转了 500 给李娜 | 转账记录 | 有，状态「待到账」 |
| 2 | 锁了卡 | 卡片面板 | 有，状态「已挂失」 |

### 截图
`截图/我的名字/01-转账确认卡.png`、`02-转账记录.png`
```

**通过标准**：

- 5 条以上，三类齐全；**「对不对」必须写**。错的就写「不对，原因是…」——**藏错不报才是没做**。
- 至少 1 条「操作可查」的对照截图。
- 页面找不到入口、或者 AI 答不上来的，**如实写进「还没做完」**，晚上一起看，不要临时改文档。

> 加分（有就写，没有不扣）：红动作被拦住 / 超范围被拒 / 断网还能打开 / 图表截图。

## 3. 交到哪、什么时候交

- **代码：新建自己的分支，发 PR 合到 `sprint/1026`，不要直接往 `sprint/1026` 上推。** 今天每人工作量都大，直接推同一个分支会互相踩，所以改成一人一分支：
  - 分支名照这个来：`feat/wangchangze` / `feat/gaojingwen` / `feat/xusiyun` / `feat/linxiaoyan` / `feat/yinchen`；
  - 提交后 `git push -u origin feat/<你的拼音>`，然后在 GitHub 上**发 PR，base 选 `sprint/1026`**，标题写「姓名 · 场景 · 一句话」；
  - PR 描述里贴：三行摘要 + 验收记录链接 + 三条门禁尾行；
  - **只 `git add` 自己改的文件**，不要 `git add -A` / `git add .`。
- **交付文件**：
  - `docs/2026-10-27/验收记录-{姓名}.md`（按 §2 ⑤ 的格式写）
  - 截图放 `docs/2026-10-27/截图/{姓名}/`
  - 王昌泽另交两份说明文档（见 §2 ③；**视频脚本今天不做**）
- **截止**：**明天（10-28）中午 12:00 前 PR 全部发出来**（今晚不用赶，做完就发、没做完明早补），**12:00–13:00** 由尹辰逐个 review + 合并。
- **合并顺序**：王昌泽 → 高靖雯 → 徐思云 → 林晓研。顺序靠后的，PR 合并前先 `git fetch origin && git rebase origin/sprint/1026`。
- **收工在群里报两样**：
  1. `pytest -q` 的尾行（证明没把别人搞坏）；
  2. 三行摘要：**改了什么 / 页面上怎么验的 / 还缺什么**，并附 **PR 链接 + 验收记录链接**。
