## 一、P0 · 演示现场会被当场戳破 / 合规硬伤

> 判定标准：评委点几下就能撞到，或与官方明文口径直接冲突。

### P0-1 红色「强验证」没有第二因子，且界面宣称有人脸 / 短信 / U 盾

| 项 | 内容 |
|---|---|
| **现象** | 红色级别的「强验证」实际只是一个请求体布尔参数，置 `true` 即过；界面却显示「等待强验证（人脸 / 短信 / U 盾）」。 |
| **证据** | `web/session.py` `confirm(..., strong_verified: bool = False)` 与闸门 `if PROMPT_STRONG_VERIFY in ... and not strong_verified`；`web/app.py` `_ConfirmRequest.strong_verified` 原样透传；`web/assets/app.js` `onConfirm()` 仅本地切 `state.phase="strong-verify"` 后再次提交；`web/assets/app.js` 文案「红色：等待强验证（人脸 / 短信 / U 盾）」 |
| **影响** | ① 权限分级最高一档可被任意 HTTP 客户端绕过；② 界面宣称了未实现的能力，与官方「不得夸大」八字相冲；③ `docs/plans/06-web-channel.md` 已自认「不是真实多因子认证」，但**必交的** `docs/security-self-assessment.md` 风险清单 R1–R8 未列此项。 |
| **修复方案** | 改为**服务端挑战-应答**：红色卡确认前须先向服务端申请验证码（`POST /api/verify/request`），服务端生成一次性、有 TTL、与 `card_id + frozen_hash` 绑定的挑战；`confirm` 改为校验 `verification_code` 而非布尔。演示环境无短信网关，验证码随响应回显并**明确标注为演示用**；接入真实短信 / 人脸只需替换一处下发实现。同步订正界面文案与自评报告。 |
| **验收** | 不带验证码 / 带错码 / 复用已用码 / 过期码 均被拒；正确码可执行；界面不再出现「人脸 / U 盾」等未实现表述。 |
| **状态** | 已修复（2026-10-07）。`web/session.py` 新增 `request_verification` + `_assert_strong_verification`（一次性 + 300s TTL + 与 `card_id`/`frozen_hash` 绑定 + 重复申请轮换）；`confirm` 的 `strong_verified: bool` 换成 `verification_code`；`web/app.py` 新增 `POST /api/verify/request`；`web/assets/app.js` 改为「申请强验证 → 输入验证码 → 提交」，文案「人脸 / U 盾」已删除；`docs/security-self-assessment.md` 补 §1.4 与 R9。 |

### P0-2 前端「中断」「回退」按钮必然失败，但界面无条件宣告成功

| 项 | 内容 |
|---|---|
| **现象** | 后端执行是在 `confirm` 单次请求内同步跑完的，返回时状态已是 `COMPLETED`，再调 `/api/interrupt` 只能拿到 409；`/api/reverse` 同理。但前端丢弃响应状态，一律渲染「已中断」「已回退」。 |
| **证据** | `web/session.py` `_execute()` 顺序同步执行；`web/app.py` `/api/interrupt` 对 `SessionStateError` 返回 409；`web/assets/app.js` `onInterrupt()` 结尾 `void result;` 且无条件 `timelineAdd("用户中断：…")`；`onReverse()` 同样不检查 `result.status`，成功后仍显示「已回退 · 回滚 N 步」 |
| **影响** | 界面对用户**谎报成功**。且这与项目自己的纪律直接矛盾——`policy/saga.py` 明确要求「不得谎称已取消」。评委点一次「中断」就能看到界面说成功、实则无事发生。 |
| **修复方案** | 前端按响应状态分支：非 200 时把服务端 `detail` 如实显示为失败，且不修改本地阶段状态。后端保持 409 语义不变。 |
| **验收** | 正常流程点「中断」显示真实的失败原因（当前状态不可中断），不再显示「已中断」。 |
| **状态** | 已修复（2026-10-07）。`web/assets/app.js` 的 `onInterrupt()` / `onReverse()` 现按响应状态分支：非 200 时显示服务端 `detail` 并保持原状态，不再无条件宣告成功。 |

### P0-3 回退不产生任何退款，但消息声称「已发起退回」

| 项 | 内容 |
|---|---|
| **现象** | 补偿函数是空操作，只写一条审计就返回；对外话术却是「本期已扣、已发起退回（补偿事务）」。 |
| **证据** | `web/session.py` `_compensation()` 仅 `self._audit(KIND_REVERSAL, {... "note": "已发起退回"})` 后 `return subject`，从不调用核心银行；`policy/saga.py` `settled=True` 分支返回 `"… 本期已扣、已发起退回（补偿事务）"`；`gateway/core_bank.py` **无任何退款 / 冲正接口**可供调用 |
| **影响** | 系统对外宣称的动作根本没有发生——不是「谎称已取消」（措辞上已避开），但「已发起退回」同样没有事实依据。 |
| **修复方案** | 让补偿**如实失败**：`_compensation()` 抛 `CompensationError`，由 `saga.reverse()` 走既有的失败分支（「补偿失败（…）：已如实告知，未宣称已取消」），审计记为 `compensation_unavailable` 而非 `compensation_requested`。真正的退款需先在 `CoreBank` 增加冲正能力，另立 P1 条目。 |
| **验收** | 回退显示「补偿失败（演示环境未接入核心银行退回通道）」；审计中不再出现「已发起退回」。 |
| **状态** | 已修复（2026-10-07）。`web/session.py` 的 `_compensation()` 改为写 `compensation_unavailable` 审计后抛 `CompensationError`，由 `policy.saga` 既有失败分支如实告知；`policy/audit.py` 的 `KIND_REVERSAL` 文档同步订正；自评报告补 §1.5。真退款仍待 P1-5。 |

### P0-4 官方定级口径偏差：理财申购、卡片解挂应为红色

| 项 | 内容 |
|---|---|
| **现象** | 官方明文列出红色包含「理财产品申购」与「挂失 / 解挂」；实现按金额档与可逆性定级，导致小额理财申购 = 黄、解挂 = 黄。 |
| **证据** | `tools/catalog.py` `wealth.subscribe` 为 `RiskClass.LARGE_FUNDS`（其 description 自己写着「官方红色典型」）→ `policy/pdp.py` `_base_decision` 走金额档，≤1000 元判黄；`tools/catalog.py` `card.unlock` 为 `SMALL_CHANGE` 且 `money_param=None` → 走 `not request.amount_applies` 分支判黄；`card.report_lost` 因 `IRREVERSIBLE` 判红（正确） |
| **影响** | 与官方口径直接冲突，属合规缺口；「理财申购」还是官方点名的红色示例。 |
| **修复方案** | 在 PDP 增加「强制红色」判定：`wealth.subscribe`（官方点名红色）与 `card.unlock`（解挂）不计金额档，直接 ≥ 红。改动落在策略层单一处，不动场景与目录的动作契约。 |
| **验收** | 小额理财申购卡为 RED；解挂为 RED；既有大额/不可逆用例不回归。 |
| **状态** | 已修复（2026-10-07）。`policy/pdp.py` 新增 `OFFICIAL_RED_ACTIONS` 与 `_official_red_modifier`（只升档不降档）；`contracts/authorization.py` 新增 `ReasonCode.OFFICIAL_RED`；评测数据两条理财申购期望由 YELLOW 订正为 RED；`eval/invariants.py` 的 `I1′`（金额序关系）把官方点名红色动作排除出可判定集；前端 `GLOSS` 补该规则码。 |

### P0-5 演示中熔断打开后**无法恢复**（除重启服务外没有出口）

| 项 | 内容 |
|---|---|
| **现象** | 一旦熔断打开，**所有非纯查询动作**都转人工接管（`web/session.py::_enter_takeover` → `SessionState.TAKEN_OVER`），而全仓**没有任何解锁入口**（`CircuitBreaker.unlock()` 无调用方），只能**重启进程**。 |
| **证据** | 2026-10-08 集成验收时 `e2e_check.py` 第 3 步红：`/api/confirm` 返回 `{"state":"taken_over","message":"转人工接管：熔断打开：非纯查询转人工接管"}`。查根因：`e2e_check.py` 自身的第 [6] 步「未知意图 → 安全拒绝」每次运行都记 1 次策略拒绝，**触发 4（连续策略拒绝 ≥3）**在跑第 2–3 次后即达到阈值 → 熔断打开；此后同一演示库上 e2e 恒红，**重启服务后立刻复现 ALL PASSED**。演示现场同理：观众提交几次未知 / 被拒意图即可把系统锁死。 |

| **验收** | 熔断打开后，通过显式、留痕的运维动作可恢复；恢复动作在审计链里有记录；「只加严不降级」的断言仍全绿。 |
| **状态** | **已修复（2026-10-08，裁决 #27）**：① `web/session.py::_refuse(..., capability_boundary=True)` —— 「未识别」不再计入触发 4；② `Session` 新增**会话级** `CircuitBreaker`，触发 3/4/5 只作用于本会话（**另一会话不受影响**，有测试断言），触发 1/2 仍作用于全局；③ `compose.build_breaker` **默认落盘**（`AIB_BREAKER_STATE=memory` 可关）；④ 新增 `POST /api/operator/breaker-unlock` + `scripts/operator_unlock.py`，`AppDeps` 尾部新增 `operator_token`（未配置 ⇒ 403），解锁前后状态 / 触发项 / 理由写入审计链（新增 `KIND_OPERATOR`）。⑤ **配套**：Web 端 `app.js` 改为**每个页面实例一个新会话**（「新开页面 = 新会话」），使会话级隔离在界面上真正生效。测试：`tests/web/test_operator_unlock.py`（5 条：未配置 403 / 口令错 403 / 缺理由 400 / 解锁 + 留痕 + 链完整 / 端到端恢复），`tests/web/test_web_integration.py` 三条熔断用例改为断言**会话级**行为。 |

## 二、P1 · 声称有、实际失效的安全机制（答辩前必须能自圆其说）

### P1-1 节点级执行门哈希是自证循环，恒真

- **证据**：`policy/pep.py` `manifest_hash(call) = cfhash((manifest_node(call),))`；`Pep.execute` 内 `assert_frozen(Plan(nodes=(manifest_node(call),)), frozen_hash)`；而 `web/session.py` `_execute()` 传入的 `frozen_hash` 恰是 `manifest_hash(call)`。`policy/gate.py` 的判据是 `cfhash(plan.nodes) == frozen_hash`——两边同为「单节点计划的哈希」，**恒等成立**。
- **影响**：`docs/security-design.md` 与 README 把「节点 ∈ 已冻结确认子图」列为注入防御的第二道防线，实际该层不存在；真正生效的只有计划级 `assert_frozen(pending.plan, frozen_hash)`。
- **状态**：已修复（2026-10-07）。`policy/pep.py` 的 `Pep.execute` 改为接收**已冻结计划**并新增 `_assert_member`（判据：动作相同 + 归一化参数逐字相等，剔除调用方注入的 `user_id`），非成员抛 `StalePlanError` 并计入熔断失败；恒真的单节点自证哈希已删除；`web/session.py`、`eval/pipeline.py` 均改为传真实计划；`manifest_plan()` 供单节点调用与单测构造。新增「越权节点」「缺少冻结计划」两条拒绝测试。

### P1-2 审计链无密钥，且运行期从不校验

- **证据**：`policy/audit.py` 的 `entry_hash` 为纯 `sha256`，`gateway/hashing.py` 无 HMAC / 密钥（全仓无 `hmac` / `secret` 引用）；`verify_chain()` 在 `src/` 下**只有定义、没有任何调用点**（调用全在 `tests/`）。
- **影响**：掌握文件写权限者可整体重写 `runtime/audit.jsonl` 并重算全链使其校验通过；运行期不做篡改检测，也无对外校验端点。
- **状态**：已修复（2026-10-07）。`policy/audit.py` 支持 `hmac-sha256` 模式（逐行 `alg` 标记、与历史无密钥行可混存迁移）；`compose.build_audit_log` **在启动时**校验历史全链，失败即拒绝启动（fail-closed）；密钥来自 `AIB_AUDIT_KEY`，未设置时用同目录 `audit.jsonl.key`。**局限已在模块与自评中如实声明**：密钥与日志同目录，不构成抗抵赖。

### P1-3 熔断「五类触发」只有 1 类真正接线

- **证据**：`policy/breaker.py` 枚举 5 类触发，但 `trip()` / `lock()` 在 `src/` 下零调用；`off_hours` / `device_change` / `high_frequency` 三个上下文标记**没有生产者**（`web/session.py` `_context_flags` 只设置 injection）；注入命中走 PDP→MANUAL，不经过熔断器。熔断状态为进程内内存（`compose.py` 每次 `build_deps` 新建），不持久化、不跨 worker。
- **状态**：已修复（2026-10-07，触发 2–5 全部接线）。`web/session.py` 新增 `_trip`（熔断 + `breaker` 审计留痕）、`_note_risky_activity`（触发 3：60s 窗口内 ≥5 次高风险）、`_note_policy_rejection`（触发 4：连续 3 次策略拒绝）；`_context_flags` 成为标记唯一生产者（注入 → 触发 2；调用方上报会话异常 → 触发 5 + `device_change` 升黄）；阈值常量落在 `policy/breaker.py`。**跨进程局限已补**（见下条）。
- **跨进程局限已修复（2026-10-08）**：新增 `policy/breaker_store.py`——`BreakerSnapshot` + `BreakerStateStore` 接缝 + `StoreBreakerStateStore`（SQLite **独立表** `breaker_state`，由 `init_breaker_schema` 自建，**不并入 01 的 `SCHEMA_SQL`**，对齐 `risk_store.py` 先例）。`CircuitBreaker(store=...)` 构造时装载、变更即落盘、读取前刷新，故状态**跨重启与跨 worker 可见**；`unlock()` 仍是唯一降级出口（可跨实例生效），`record_success()` 在 `OPEN` 时依然不改状态（只加严不降级）。装配在 `compose.build_breaker`，由 **`AIB_BREAKER_STATE`** 开关控制。
  **默认不启用**（纯进程内，行为与原先逐字一致），理由如实说明：一旦 `OPEN` 落盘就会跨重启保留（这正是「只加严不降级」的正确语义），但本项目**尚无运维解锁入口**，默认开启会锁死演示现场；生产多 worker 部署应开启。**残留局限**：多写者下连续失败计数为「尽力而为」（后写覆盖，随后被聚合回较大值），**权威的是状态位**；`tests/policy/test_breaker_store.py` 11 条用例覆盖跨实例可见性、跨实例不降级、解锁传播与表独立性。


### P1-4 沙箱不运行生成代码，且隔离非 OS 级

- **证据**：`gateway/sandbox.py` 以 `subprocess` 执行 `sandbox_child.py`，只跑 `gateway/operators.py` 白名单内的 5 个确定性数值算子（调用点仅 `scenarios/bills.py` 与 `eval/pipeline.py`）；隔离手段为 Python 层 monkeypatch（禁 socket / 禁库 / 禁写）+ 超时，无容器、无 seccomp、无 namespace、无 rlimit。
- **影响**：官方字面要求「生成的代码在受限、可监控的逻辑隔离环境中运行」。这是**主动设计偏离**（README 与 `official-requirements.md` 已自认），需在答辩中给出「为何不生成代码」的正面论证，而非默认满足。
- **状态**：不修（附理由）——本方案全链路无代码生成，把沙箱用于确定性算子是有意取舍；补的是**说明**不是实现。

### P1-5 真实退款通道缺失（P0-3 的根治方案）

- **证据**：`gateway/core_bank.py` 提供 `transfer` / `unfreeze_funds` / `set_card_status` 等写接口，但**没有任何冲正 / 退款接口**，故 saga 补偿无法落地为真实资金动作。
- **修复方案**：在 `CoreBank` 增加幂等的冲正接口（与 `transfer` 同构，写回平衡分录 + 回执），再由 `web/session.py` 的补偿函数调用它。
- **状态**：已修复（2026-10-07）。`gateway/core_bank.py` 新增 `reverse_transfer`（校验流水存在且为流出 → 回补余额 + 写 `category='冲正'` 反向分录，沿用幂等键）；新增 `policy/reversal.py` 的 `ReversalService`（跳过错过的无资金影响记录，真正失败如实抛 `CompensationError`）；组合根装配 `AppDeps.reversal`；`web/session.py` 的 `_compensation` 改为调用该通道，并**去掉了调用方可控的 `settled` 参数**（模拟核心银行执行即结算，故一律走真实补偿）。回退现在会**真正回补余额**并留下冲正分录。

#### 步骤 1 过程中的三个设计订正

1. **`kind` 最终采用「字段可空 + 派生处把关」，而非必填。** 先试了必填，结果连带
   **14 处测试构造**（`tests/tools/test_registry.py` 13 处、`tests/policy/conftest.py` 1 处）
   全部报 `missing 1 required positional argument`。测试替身不该被强制声明类别，
   故改为：`ToolSpec.kind` 可空，但 `planning.llm._kind_of()` 在派生时校验
   「规范目录每项都必须声明类别」，缺失即 `ValueError` **fail-fast**。
   这样 totality 仍被强制，代价没有错配到测试上。
2. **新发现一张待派生的平行表：`planning/slots.py::SLOT_PARAMS`**（槽位名 → 参数名，
   如 `account`→`account_id`、`amount`→`amount_cents`）。它现在与 `ParamSpec.slot_name`
   **语义重叠**——两者都编码「槽位名 ↔ 参数名」。步骤 1 完成后应把它一并改为派生，
   否则它仍是一处需要手工同步的争用点。**记为 1.3 的后续项**。
3. **1.2b 原写法作废：把 specs 下移到场景模块会形成循环依赖，且属反向依赖。**

#### ⚠️ 步骤 1 试做结论（2026-10-07，已试做 1.3 后回滚）

**1.3 试做失败，且失败原因证明「派生」缺两个字段。** 试做内容：把 `REQUIRED_SLOTS` 改为
`{action: tuple(p.name for p in spec.params if p.required and p.slot is CONTROL)}`。
结果测试大面积报 `KeyError`，暴露**两套词汇表不同**：

| 来源 | 词汇 | 实例 |
|---|---|---|
| `REQUIRED_SLOTS`（**策划层槽位名**） | 槽位名 | `account`、`card`、`subscription`、`amount`、`when`、`payee`、`hold` |
| `ToolSpec.params`（**执行层工具参数名**） | 参数字面名 | `account_id`、`card_id`、`subscription_id`、`hold_id`、`year`、`month`、`start`、`end` |

即：`account` ≠ `account_id`、`card` ≠ `card_id`、`subscription` ≠ `subscription_id`、
`hold` ≠ `hold_id`，且 `bills.monthly` 的槽位是 `user_id` 而参数是 `year`/`month`。
**两者不是同一个东西，无法互相推导。**

**另一处同类问题（1.4）**：`ACTION_KINDS` 的 `ActionKind` ∈
{QUERY, OUTFLOW, INFLOW, CANCEL_OUTFLOW, STATE, IRREVERSIBLE}，而 `ToolSpec.risk` 只有 5 档风险；
`wealth.subscribe`(OUTFLOW) 与 `wealth.redeem`(INFLOW) **同风险**、
`subscription.cancel`(CANCEL_OUTFLOW) 与 `card.lock`(STATE) **同风险** ⇒
**类别不可由 `risk` 推出**，且 `ActionKind` 定义在 `planning/llm.py`，
下移到 `tools/` 才不违反依赖方向。

**结论：步骤 1 需要先给工具契约补两个字段**（属 `tools/` / `contracts/` 层改动，
按 `AGENTS.md` 第 4 节需**团队一致同意**）：

1. `ToolSpec.kind: ActionKind` —— 并把 `ActionKind` 从 `planning/llm.py` **下移**到 `tools/registry.py`；
2. 槽位名映射 —— `ParamSpec.slot_name: str | None`（参数名 ↔ 槽位名），
   或 `ToolSpec.required_slots: tuple[str, ...]`。

补完这两个字段，1.2 / 1.3 / 1.4 才是**赋值式改动**而非结构改动；否则每一步都要靠手写映射表，
等于把争用从一个文件搬到另一个文件，**没有真实收益**。

**真正的收益来自聚合点**：让**每个场景模块自带自己的 `ToolSpec`**，`catalog.py` 只做聚合
（遍历场景模块）。这样给**已有场景**新增动作 = **只改自己那一个场景文件**，`catalog.py` **零改动**——
这才是「各做各的、无先后」的关键，光把字典改成派生还不够。

**前置检查项**：`tools/registry.py::ToolSpec` 是否已带「动作类别（查询 / 变更）」与
「必填控制槽」信息。若没有，须先补字段——这属 `contracts/` / `tools/` 层改动，
按 `AGENTS.md` 第 4 节需**团队一致同意**。
