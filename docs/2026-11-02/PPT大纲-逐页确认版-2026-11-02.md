# 第 2 页｜银行 AI Agent 的核心难题

## 页面内容

- 标题：银行 AI Agent 的核心难题，不是“会不会聊天”，而是“能不能可信地办事”
- 页面中心放置一个“自然语言请求 → 银行操作”的转化链，周围标出四个必须同时解决的技术难题：
  1. **意图理解难**：用户经常使用口语、省略和模糊表达；系统必须识别真实意图，补全金额、对象、时间、账户等关键槽位，缺少信息时要主动澄清，不能靠模型猜测。
  2. **任务规划难**：一个请求可能包含多个动作、先后依赖和条件分支，例如查询账单后判断预算，再锁定资金并安排生日消费；Agent 需要生成可校验的 Plan / DAG，而不是只返回一段文字。
  3. **安全执行难**：模型可以提出转账、解锁、申购等动作，但不能直接获得银行执行权；系统必须区分查询、用户确认、强验证、人工接管和拒绝，并防止计划在执行前后被篡改。
  4. **结果可信难**：金融系统不能编造余额、交易结果或执行成功状态；每个关键结论需要有事实来源、审计记录、业务回执，并能处理中断、失败、补偿、回退和异常熔断。
- 页面底部结论：`银行 Agent 的竞争力 = 更自然的理解能力 + 更严格的执行边界 + 更完整的事后证明能力`

## 页面讲解重点

这一页要先建立评委对问题难度的共同理解。银行 AI Agent 与普通客服问答的区别，不在于能否生成自然语言，而在于它必须把不完整、带上下文的用户表达，转换成一份可以被验证和执行的金融任务。当前代码中，Session 会保存对话和任务状态，在信息不足时进入澄清，而不是让模型自行补值；Planner 需要输出结构化意图，场景层再将其组织为带依赖关系的 Plan；Reviewer 负责检查计划是否偏离用户原始意图；PDP 和 PEP 将模型提案与实际执行权限隔离；事实网关、回执、审计、失败补偿和回退机制，则负责回答“系统到底做了什么、结果是否真实、出错后能否收回来”。因此，本项目解决的不是单点聊天体验，而是从理解、规划到执行和证明的完整可信链路。

# 第 3 页｜我们的 AI 如何解决这些难题

## 页面内容

- 标题：从“理解需求”到“安全办事”，我们的 AI 不是只生成答案，而是生成可被系统接管的任务
- 页面用“四个难题 → 四个解决机制 → 产品结果”的对应关系展开：
  1. **面对模糊表达**：AI 先生成结构化意图和候选槽位；当收款人、金额、时间或账户存在歧义时，系统进入澄清流程，不直接猜测。产品结果是：用户可以用自然语言提问，系统会追问真正影响执行安全的缺失信息。
  2. **面对复杂任务**：AI 将请求转换为带动作、参数、依赖关系和意图锚点的 Plan / DAG；多个动作必须按照依赖顺序执行，计划在确认后冻结，不能被后续文本悄悄改变。产品结果是：复杂请求可以被看见、被审查、被中断。
  3. **面对金融风险**：AI 只负责提出候选方案，PDP 根据动作类型、金额、累计净效应、对象状态和可逆性重新裁决；低风险查询自动完成，写操作进入确认、强验证、人工接管或拒绝。产品结果是：同一个对话界面可以明确呈现黄色确认卡、红色强验证卡和安全拒绝。
  4. **面对事实和结果可信问题**：账户、账单、交易和回执来自事实网关与模拟核心银行，模型不能自行编造数字；执行过程写入审计链，失败时保留状态并支持重试、补偿说明和回退。产品结果是：用户不仅看到回答，还能看到操作依据和执行结果。
- 页面底部结论：`AI 负责理解与规划，确定性系统负责约束与执行，产品界面负责让用户看得见、确认得了、追溯得到。`

# 第 6 页｜核心技术二：从语义计划到银行式交易工作流

## 页面内容

- 标题：把 AI 的计划变成用户可修改、可确认、可验证、可回执的银行操作
- 核心技术名称：`Plan / DAG + Immutable Frozen Plan + Transaction Draft + PDP / PEP`
- 页面展示一条新的银行式交互链：
  `语义帧 → 场景装配 → Plan / DAG → Transaction Draft → 用户修改 / 澄清 → 冻结计划 → PDP 权限 → 确认或强验证 → PEP 执行 → Receipt`
- 重点说明四个技术关系：
  1. **Plan / DAG**：多个动作以节点和依赖关系表达，生日场景可以先登记预算 / 预约，再在到期时重新提案，不能把未来动作提前执行。
  2. **Transaction Draft**：写操作先生成服务端校验的交易草稿，用户只能修改允许字段；修改金额、备注或产品后，旧确认立即失效，系统重新生成执行 ID 和计划哈希。
  3. **PDP / PEP 分工**：PDP 依据风险、金额、累计净效应、对象状态和可逆性裁决 GREEN / YELLOW / RED / MANUAL / DENY；PEP 只执行已授权、已冻结、属于白名单的动作。
  4. **用户可见边界**：黄色显示确认卡，红色进入一次性挑战和验证页面，拒绝显示原因；同一页面不能同时展示过期草稿和可确认的旧计划。
- 页面底部结论：`AI 可以自主规划，但每一次金融写操作都必须经过服务端草稿、冻结计划和权限门。`

## 页面讲解重点

这一页把“规划”与“执行”之间的工程边界讲清楚。AI 输出的不是一个立即执行的按钮，而是一份可审查的结构化计划；场景层根据节点、依赖、时间和对象把它装配成 DAG，系统再把写操作转换为交易草稿。草稿允许用户修改有限的业务字段，但不允许修改权限等级、计划哈希、对象归属或验证结果。任何修改都会使原确认失效，并由服务端重新生成执行 ID 和冻结计划，防止用户确认的内容与最终执行内容不一致。PDP 只负责裁决风险，PEP 只负责执行已经通过裁决的白名单动作，两者都不依赖模型临场决定。这样，AI 的灵活性被保留在理解和规划阶段，而真正的资金、卡片、理财和代扣操作仍然经过可见、可确认、可验证的银行式流程。

# 第 7 页｜核心技术三：事实可信、安全闭环与可验证证据

## 页面内容

- 核心技术名称：`Fact Gateway + Zero-Fabrication + Audit Hash Chain + Breaker / Recovery + Strict-Model Evidence`
- 页面从“模型可能犯什么错”切入，展示系统的五道可信防线：
  1. **事实零生成**：余额、交易、账单、收益、对象信息全部来自 Fact Gateway；模型只能选择结构化叙事和措辞，不能自由生成金融数字。

  4. 依据生日前 2 天生成预约时间；

- 强调最新方案的语义边界：只有明确说出订单金额，才允许进入订单节点；“预算 800 元”不能自动变成“下单 800 元”。
- 说明未来日期不提前冻结、不提前下单；确认时登记预约，到期重新提案并二次确认，避免提前占用资金或额度。
- 底部结论：`一句话多动作，不等于一次性放行；DAG 负责拆分，PDP 负责逐节点裁决。`

## 页面讲解重点

这是项目最能体现 Agent 价值的跨场景案例。普通聊天机器人可能把“预算 800 元”理解成“马上花 800 元”，而本项目把预算约束、订单金额、时间和预约状态分成不同语义角色，并将多个动作装配成 DAG。未来日期的请求在当前时点只生成预约和计划，不会提前扣款、冻结或下单；到期后由调度入口重新提出候选动作，用户再次确认后才执行。即使是同一句话产生的多个节点，也不能因为整体意图看起来合理就共享一次授权，PDP 会按节点和计划净效应取最严级别。这个场景同时证明了自然语言交互、复杂任务规划、跨资源域协调和安全执行边界，是全套答辩中最有辨识度的闭环。

# 第 11 页｜Web、PWA、飞书多渠道演示

## 页面内容

- 标题：同一套安全内核，适配 Web、可安装 PWA 与飞书 IM
- 页面先明确渠道口径：
  1. **Web**：完整桌面工作台，适合展示计划卡、账单面板、审计记录和多步骤任务。
  2. **PWA**：同一份 HTML 的可安装移动端形态，窄屏自动切换底部四 Tab，适合手机端快速查询和确认。
  3. **飞书 IM**：真实回调链路，包含验签、AES 解密、身份绑定、事件幂等、限流和卡片回调；飞书负责消息和卡片交互，执行仍回到统一会话与策略内核。
- 页面展示“同一请求，不同入口”：Web 发起转账、PWA 查看账单、飞书收到风险确认卡；三者共享账户事实、权限规则、审计和执行器，但不共享不应共享的对话上下文。
- 明确演示边界：飞书不是单独实现一套业务逻辑，回放模式只作断网兜底；红色高风险动作可引导回 Web 完成强验证，不能在 IM 中伪造真实 MFA。
- 底部结论：`渠道可以变化，权限和执行语义不能分叉。`
