## 0. 一页结论

1. **两套评分口径结论一致，不要被分数差异误导。**
   - 官方三维（任务完成率 40 / 安全合规 30 / 创新与交互 30）自评 **66/100**；

   - 两者相差不到 1 分，指向同一个病灶：**技术本体是全场前列，交付物接近 0。**
2. **1562 个测试不产生任何分数。** 盲审评委不跑代码，只看 PPT / 视频 / 文档 / 结果表；自动评测只看服务行为与场景完成率。
3. **冲十强的分数缺口 ≈ 14 分，几乎全部在"可被看见"的部分**：
   - 交互与创新 30 分里只拿到约 16（无量化、无对标、渠道弱、演示未打磨）；
   - 任务完成 40 分里丢约 8（理财"推荐"语义、跨场景未锁资金、APP/IM 渠道）；
   - 安全合规 30 分里丢约 6（机制强但**没有一个实测数字**）。
4. **本周只做三件事：补完成度、补证据、补叙事。不铺新架构、不新增业务动作。**
5. **关于"不冻结"：** 采纳"本周必须做完"的判断，但把它落成**三层冻结**才可控——
   - 10/31 23:00 **功能封版**（只修 bug，不加功能）；
   - 11/01 20:00 **代码冻结**（打 `v1.0-submission` tag、打包、录屏备份）；

## 4. 本周方向：把"不冻结"变成可控的冲刺

### 4.1 三层冻结（采纳你的"必须做完"，但加上止损线）

| 时间 | 状态 | 允许 | 禁止 |
|---|---|---|---|
| 10/26–10/30 | 开发期 | 5 项功能补口、证据、材料并行；组长可做**架构收口**（权限裁决与规划内核的确认 / 修改） | 重写架构、组员擅改内核 |
| 10/31 23:00 | **功能封版** | 只修 P0/P1 bug | 任何新功能、任何 UI 重构 |
| 11/01 20:00 | **代码冻结** | 打 tag、打包、录屏、离线彩排 | 改任何代码/文档数字 |
| 11/02 | **提交日** | 上传、核对清单 | 改文件（含"顺手改一下"） |

理由：你说"最终提交不允许再修改"，那真正的风险不是"冻结太早"，而是**11/01 晚上还在改代码，导致提交版没被完整验证过**。三层冻结保障的是"提交的那一版 = 彩排的那一版"。

### 4.2 五条战线与优先级

| 战线 | 内容 | 优先级 | 判定标准 |
|---|---|---|---|
| ① 完成度 | ③适当性闭环、⑥资金冻结、渠道 | P0 | 六场景每个都能用一句话讲清"做了什么、拒了什么" |
| ② 证据 | benchmark 双通道、四个数字、交互指标 | P0 | 数字可复跑、口径写清、CSV 可查 |
| ③ 叙事 | PPT、视频、简介、README、对标表 | P0 | 10 分钟能讲完，且不宣称未实现能力 |
| ④ 演示 | 公网 Demo、重置、离线兜底、彩排 | P0 | 连演三遍结果一致 |
| ⑤ 治理 | tag、worktree、数字统一、CI 记录 | P1 | clone 一条命令可复现 |

### 4.3 明确不做（写进团队共识，防止"完善"变"发散"）

- 不新增业务动作（当前 25 个已够）；
- 不重写架构、不改零信任双核边界；
- 不接真实银行 / 真实支付 / 真实 IM 生产环境（最小真 IM 只做"能收发一条消息"的级别）；
- 不为让指标好看而放宽语义断言或删对抗样例；
- 不补第 7 个场景、不做多语言、不做用户体系；
- 不把 `wt-data` 的新功能硬塞进来——除非它已在 `2bcffeb` 上通过全量测试。

## 5. 分工：一人一摊

> 流程真源：[docs/分工文档-2026-10-26.md](分工文档-2026-10-26.md)（D1–D8 交付包 / 八工位 S0–S7 / 每日节奏 / 文件归属 / agent 提示词）；当天要交什么看 [docs/交付清单-2026-10-26.md](交付清单-2026-10-26.md)。本节只放结论，细则一律以那两份文档为准。

### 5.1 为什么不按"能力切"

vibecoding 下，按能力切（一人只做证据、一人只做材料）会立刻出现两个问题：跨人交接成本高、材料与实现脱节。改成**一人一个场景端到端**后，每个人的活都能独立验收，组长只需要验标准、改架构、做合并。

### 5.2 分工表

| 人 | 场景 | 附加职责 |
|---|---|---|
| **尹辰（组长）** | ⑥ 跨场景联动（生日锁 1000 → 订花 → 扣款） | 架构完善、三色基准表、`catalog` / `policy` / `kernel` 变更、合并与裁决、10/28 答疑、PPT 统稿、答辩主讲、tag 与提交、**视频剪辑统筹** |
| **王昌泽** | ⑤ 订阅 + **渠道** | PWA / IM 接通、公网 Demo、一键重置 |
| **高靖雯** | ① 智能转账 | 做出**三色分级最完整的样板**，其他人照抄 |
| **徐思云** | ③ 理财（风险测评 → 适当性 → 申购 / 赎回） | 做出**强验证链路样板**（红色动作的标准写法） |
| **林晓研** | ② 账单 + ④ 卡片 | ② 补异常交易识别；④ 补挂失 / 解锁 |

每个人都要做自己的**前后端 + 测试与证据 + 材料**（即 D1–D8 全套），不存在"我只写文档"或"我只写后端"。

### 5.3 协作机制（只保留不可外包的三件）

- **每日 09:30 站会**：每人 3 分钟，只报「昨天交了哪几件 D / 今天交哪几件 D / 卡在哪」；组长只回「可以」或「改成 X」，不当场展开讨论。
- **每日 18:00–19:00 合并窗口**：顺序 王昌泽 → 高靖雯 → 徐思云 → 林晓研，后合者负责重放冲突；主干始终可跑。
- **每日 19:00**：组长更新「架构问题清单」+「成绩单」；跨场景的架构问题在这里一次性收口，不做点对点私聊修补。

补充规则：
- **合并门禁**：只有组长合并；合并前必须 `ruff + mypy + pytest` 全绿 + 服务自检（见 `AGENTS.md`）。
- **共享文件**：`tools/catalog.py`、`policy/*`、`planning/kernel.py` 仅组长；`web/app.py` 按路由认领；`web/assets/app.js` 按场景块认领；`README.md`、`docs/作品简介.md` 分段认领、组长统稿。
- **不静默改口径**：任何指标定义变化必须写进 `RESULTS.md` 的"口径变更"一行。

### 7.3 作品简介重写（示范稿，D 线定稿时按官方 ≤200 字复核）

> 银行最怕的不是 AI 不会做，而是它做错了还很自信。AI 银行副驾用"零信任双核"约束大模型：规划内核拆意图、补槽位；执行内核以 PDP/PEP、计划卡、强验证和撤销补偿守住每笔资金动作。数字与实体只来自确定性网关，模型只说措辞、不握执行权；注入、越权、控制槽篡改与超范围请求被类型层和执行门阻断，全程可审计、可中断、可回退、可接管。手机网页一句话即可办理转账、账单、理财、卡片、订阅与跨场景任务，让不熟悉 App 的人也能安全使用银行服务。

三段结构：**技术主张（双核）→ 安全证据（四类阻断 + 可恢复）→ 普惠价值（不熟悉 App 的人）**，且每一句都有代码落点。
