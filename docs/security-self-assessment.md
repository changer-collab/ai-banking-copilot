### 1.3 硬化规则

- 绿色**只含纯查询**；任何资金 / 状态变更不得落入绿色（构造层与目录层各有一条断言）。
- 冲突取**更严**级别并**并集**原因（可解释）；对象维度**只升档不降档**；`blocked` 为**吸收态**。
- `untrusted` 永不进控制槽（类型层拒绝）；多候选收款人**不产出级别**（强制澄清）。
- 熔断**只加严不降级**；沙箱**不得回写事实网关**；执行后必须做数值出处校验。
- **执行门双层**：计划级 `assert_frozen(plan, cfhash)` + 节点级**成员资格**（`call` 必须属于已确认计划）；
  确认后改动金额 / 收款人 / 账户 ⇒ 不再是计划成员 ⇒ `StalePlanError`（2026-10-07 修复，原节点级判据为恒真）。
- **审计链启动严格校验**：先要求密钥与原全链校验通过，再检查算法；接受空链、完整 HMAC，
  或首条 HMAC 为 `audit_migration` 且精确绑定连续 SHA 前缀条数和链头的日志。纯 SHA、无迁移锚混链、HMAC 后 SHA 均拒绝。
  旧链只能停服务后用 `scripts/migrate_audit.py`、外部可信锚与不覆盖备份显式迁移；低层兼容校验不等于服务信任。
- **熔断五类触发全部接线**：注入 / 滑动窗口高频 / 连续策略拒绝 / 调用方上报会话异常 + 原有连续授权失败；
  每次状态从关闭转为打开时写 `breaker` 审计事件，包含触发项、范围、状态与可用的关联身份；保持打开期间的重复拒绝不重复记为新转换。
- **强验证失败计数**：默认组合根为每用户计数注入独立 RW SQLite 存储，失败次数与锁定跨会话、worker 和重启共享；手工构造 `AppDeps` 的测试默认仍是进程内。挑战本身仍按当前会话流程管理，不宣称持久化。
- **事实零生成的叙事边界**：账单模型只返回已登记的摘要、解释与建议 ID，由服务端按事实渲染；严格 Reviewer 只接受空 `findings` / `clarifications`，澄清和接管文案由服务端模板产生。模型无法把自写事实展示为审查理由。
- **受限分析沙箱**：只执行白名单表达式 DSL，不执行任意 Python；源值必须来自快照且结果保留全部原始 `record_id`。POSIX 使用 `rlimit`，Windows 使用 Job Object 和父进程 watchdog；限制能力不等于容器级隔离。
- **理财资金守恒**：申购校验起购金额与余额，并同事务累加 `wealth_holdings`；赎回校验「持有且不超持仓」，起购价不再拦截赎回（2026-10-28 关闭 R20）。

### 1.4 强验证（红色）的落地形态与边界

**实现**：红色卡在确认前必须向服务端申请一次性挑战（`POST /api/verify/request`），
服务端生成验证码并持有，`Session.confirm(..., verification_code=...)` 校验四个条件后放行：

| 条件 | 说明 |
|---|---|
| 服务端下发 | 必须存在服务端挑战；未申请即提交任意值一律拒绝（不再接受任何客户端布尔标志） |
| 一次性 | 校验通过即消费；重复申请**轮换**验证码，旧码立即失效 |
| 有效期 | `VERIFICATION_TTL_S = 300` 秒，过期须重新申请 |
| 执行与计划绑定 | 挑战与 `execution_id` + `card_id` + `frozen_hash` 绑定；新提交、换计划或授权升级即失效 |

**如实声明的边界（重要）**：本仓库**未接入真实短信 / 人脸 / U 盾渠道**。演示环境无第二信道，
验证码随 `/api/verify/request` 的响应回显以便路演现场输入——因此它**不是密码学意义上的
双因子认证**，而是「服务端一次性挑战」的可演示实现。接入真实下发渠道时只需替换**下发一步**，
上述四条校验逻辑不变。

同时已按官方口径订正定级：`wealth.subscribe`（理财申购）与 `card.unlock`（解挂）强制 ≥ 红
（`policy.pdp.OFFICIAL_RED_ACTIONS`），不因金额小或动作可逆而降为黄。

### 1.5 回退（撤销 / 补偿）的落地口径

模拟核心银行**执行即结算**，故不存在「尚未结算 ⇒ 无扣款」这一档：回退**无条件走补偿事务**，
对本条执行的每条回执逐条处理：

| 记录类型 | 处置 |
|---|---|
| 流出流水（转账等） | 调用 `CoreBank.reverse_transfer` **真正回补余额**并写 `category='冲正'` 反向分录（沿用幂等键） |
| 无资金影响的记录（纯查询等） | 跳过（没有可回退的资金影响），审计记 `nothing_to_reverse` |
| 冲正失败（流水不存在等） | 如实返回 `failed` 并说明原因，审计记 `compensation_failed` |

未装配冲正通道（`AppDeps.reversal is None`）时一律**如实失败**，审计记 `compensation_unavailable`。
补偿经组合根注入的 `ReversalService` 处理本执行回执，是既有 TCB 受控回补路径；
剩余新业务升档、清除确认不妨碍回补已完成转账。存在已提交但未核验回执时，必须先恢复核对再回退。
**任何情况下都不宣称「已取消」**——措辞与状态一律取自 saga 的如实告知（2026-10-07 起由「如实失败」
升级为**真实冲正**，见 `docs/已修复清单-2026-10-08.md` P0-3 / P1-5）。

### 1.6 执行一致性与可信调用边界（2026-10-16）

完整 DAG 冻结包含节点 ID、参数、授权锚、依赖和执行顺序；新提交拥有独立执行 ID，重试复用原键。
每个业务节点在同一事务内按实际结算日复核最新累计与熔断；完整计划正向流出不被赎回抵扣，已完成转账不双计。
风险升档保留已完成节点并重新确认；恢复必须匹配本执行确认与必要的强验证。提交后核验 / 审计失败明确报告已提交回执，停止后续并以原键恢复。

旧 `Pep.execute` 程序化入口中的 `Decision` 是 **TCB 提供的可信授权上限**，仍强制复核最新风险；
可信调用方给出的红级授权不等同 Web 验证码证据。外部 Web / IM 请求不能注入 `Decision`、执行上下文或强验证布尔值，必须经过 Session 的确认与挑战。

## 三、自评结论

- 官方五项安全机制（权限分级 / 幻觉防护 / 注入防御 / 操作审计 / 异常熔断）+ 沙箱**均有实现落点与测试证据**。
- 强硬约束（绿色纯度 / 吸收态否决 / **计划级**冻结校验 / 熔断只加严 / 沙箱不回写 / 撤销不谎称已取消）**均有断言**；**节点级**执行门已于 2026-10-07 由恒真判据改为**成员资格校验**（见 R10）。
- 界面与实现一致：红色不再宣称「人脸 / U 盾」，中断失败如实报错，回退由「如实失败」升级为**真实冲正**（回补余额 + 反向分录）。
- 工程门禁由 Ruff、严格 mypy、全量 pytest 和模板服务自检组成；当前提交的执行结果以 CI 与 PR 验证记录为准。
- 能力边界如实声明：**不证决策正确、不证泛化、LLM 侧有抖动、降级通道非等价实现、强验证无真实第二信道**。
- 官方六场景 × 25 项点名能力：**25 项有 · 0 项半有 · 0 项无**，逐条对照见 [official-requirements.md](official-requirements.md)。R17 / R18 / R19 / R20 / R21 / R22 / R23 已关闭，R16 升至 7 类，**R15 于 2026-10-31 关闭**（完整手机号逐位匹配）。
- 2026-11-02：动作集扩至 28 个（补卡 / 信用卡额度 / 周期限额），新增 R24–R28 五项已知风险；卡片、理财、账单、代扣、转账五处能力边界均在界面与文档中如实标注。
