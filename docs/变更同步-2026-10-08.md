## 一、修掉的问题（按"评委视角"分四档）

### 第一档：演示现场会被当场戳破 / 合规硬伤（5 项，全部已修）

1. **最高权限级（红色）的"强验证"是假的**
   原本只是请求里的一个开关，任何客户端把它置成"已通过"就能执行；界面上却写着"等待人脸 / 短信 / U 盾"。
   → 改成**服务端一次性挑战码**：有有效期、和这一笔操作绑定、用过一次就作废；界面不再出现未实现的字眼。

2. **"中断""回退"按钮必然失败，但界面一律显示成功**
   后端是在确认那一次请求里同步跑完的，点按钮只会拿到冲突错误；但前端丢掉了错误、无条件渲染"已中断 / 已回退"。
   → 改成**如实反映**结果，不再谎报成功。这与项目自己"不得谎称已取消"的纪律一致。

3. **回退不产生任何退款，对外的说法却是"已发起退回"**
   补偿逻辑其实是个空操作，只写了一条日志。
   → 先改成**如实失败**（"演示环境未接入核心银行退回通道"），随后在第二档里补上了**真实的退款通道**。

4. **权限定级口径与官方明文冲突**
   官方点名"理财申购"和"挂失 / 解挂"应属最高级，实现却按金额算，导致小额理财申购变成了中等级。
   → 这三类改为**强制最高级**（只升档、不降档）。

5. **系统会"自己把自己锁死"，而且解不开**
   安全闸门一旦锁定，除了重启服务没有任何恢复办法；更糟的是**"用户说了句系统听不懂的话"被记成了"恶意试探"**，连说两三次就把整个系统锁死——演示现场观众点几下就能撞到，并且会**伪装成别的故障**（我们这次差点误判成合并回归）。
   → 详见第三节第 1 条，这是本轮**最要紧的一项修复**。

### 第二档：宣称有、实际失效的安全机制（5 项，4 修 1 判定不修）

1. **"这道防线"其实不存在**——执行前有两道校验，第二道是"拿这步的哈希去比这步的哈希"，恒等成立、等于没有。而文档里把它写成了注入防御的第二道防线（**文档比实现更乐观**，这是最危险的一类）。
   → 改为真正核对"当前这一步是否属于用户已确认的那份计划"，越权节点直接拒绝并计入安全闸门。

2. **审计日志可以被悄悄整条重写**——原本没有密钥，运行期也从不校验；能写文件的人可以改完再重算整条链，校验照样通过。
   → 改为**带密钥**，并在**启动时校验历史全链**，对不上就拒绝启动。局限（密钥与日志放同一目录，不构成真正的抗抵赖）已在安全自评里如实写明。

3. **安全闸门宣称有"五类触发"，实际只有 1 类真的接了线**（其余三类连"信号从哪来"都没有）。
   → 五类全部接上：注入检测、连续授权失败、高频高风险、连续被拒、会话异常。并新增"状态可以跨重启、跨进程保留"的能力。

4. **没有真实的退款通道**（就是上面第 3 条的根治方案）。
   → 新增冲正能力：现在**回退会真正把钱补回来**，并留下冲正分录。

5. **沙箱不运行"生成的代码"，隔离也不是操作系统级** —— **判定不修**，理由：本方案全链路**不生成代码**，沙箱只用来跑确定性的数值计算。这是**主动的设计取舍**，我们补的是"说明"而不是实现，答辩要正面给出"为什么不生成代码"的论证。

### 第四档：交互与工程问题（7 项，全部已修）

1. **计划里的执行顺序从不按依赖关系走**——虽然画了依赖图、也能检测环，但执行时就是照列表顺序来。
   → 改为**按依赖顺序执行**（顺序确定、可复现），并且每一步执行前先确认"它依赖的步骤都已完成"，没满足就拒绝执行（宁可停下也不冒险）。
2. **低置信度的意图被悄悄丢掉**——多意图时用户根本不知道漏了一条。
   → 改为**明确告知**："另有 N 条意图置信度不足未采纳：…"。
3. **澄清没有闭环**——用户回答后系统把上下文清了，等于白问。
   → 现在会**保留原意图**，回答后接着走完。
4. **"撤销窗口"形同虚设**（每次重建、永不过期）→ 改为**不再走窗口，直接做真实补偿**（见第二档第 4 条）。
5. **两套前端样式靠人工同步、已经开始分叉**（主仓与设计仓各一份，且出现只有一边有的规则码）。
   → 新增**自动比对脚本**：样式文件不一致直接判失败，规则字典差异只告警（设计仓是示意版，可能有意）。**真正的同步机制（子模块/构建期生成）仍待团队裁决。**
6. **前端有个字段一直是"死赋值"**（后端返回的名字和前端读的名字对不上）→ 已清理。
7. **运行目录没被忽略** → 已加入忽略（含审计日志与本机密钥文件），避免误提交。

## 三、三个"看不见、但最要紧"的底层改动

### 1. 安全闸门不再"自己把自己锁死"，并且终于有了解锁出口

- **误判修正**：听不懂用户的话 = **能力边界**，不是"用户在做恶意试探"。原来这两种情况被混为一谈，导致连说三次听不懂就把系统锁死。
- **范围分层**：**系统级的危险**（注入攻击、连续授权失败）才全局锁；**单个会话的行为异常**只锁他自己那个会话，其他人不受影响。
- **状态存盘**：锁定的状态存进数据库，**重启不能绕过**（原来重启即复位，等于给安全机制留了后门）。
- **唯一解锁出口**：新增一个运维解锁入口——**要口令、必须写理由、解锁前后状态全部进审计链**。口令没配置就一律拒绝（宁可不能用，也不留缺口）。
- **配套**：网页改成"每次打开页面算一次新会话"，让会话隔离在界面上真正生效。

### 2. 加新功能不用再动"心脏文件"

- 原来："有哪些动作、每个动作需要哪些信息、谁来执行"散在好几处**手写清单**里，每加一个动作都要改同一个核心文件——**四个人并行开发必然改同一行、必然冲突**。
- 现在：这些都从**唯一一张动作总表**自动推导，各业务模块自己带执行逻辑。
- 效果：这轮四个人能**真正并行**，合并时只剩几处"相邻两行各加一句"的文本冲突，取并集即解。

### 3. 演示库"补数据"不用重建、也不会覆盖你的演示

- 原来：检测到数据库初始化过就整段跳过——所以这轮新加的 18 个月历史数据，**老的演示库永远拿不到**，还是显示"不可判"。
- 现在：**一条一条补齐、已存在的不动**。老库自动补上新数据，同时**不覆盖你演示时真实产生的变化**（余额、卡片状态、你发起的交易全部保留）。
- 实测：在**未重建的旧演示库**上直接启动，年度账单已显示 +17.65%。
