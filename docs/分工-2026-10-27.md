## 2. 生活场景怎么归类：三个维度 → 七条原型

任何一件「要用银行办事的生活事件」，都可以拆成三个正交问题：

| 维度 | 问题 | 取值 |
|---|---|---|
| **A 时间形态** | 这笔钱什么时候动？ | A1 一次性（现在） / A2 先备后花（锁一段时间） / A3 周期性（每月） / A4 到某天必须完成 |
| **B 资金形态** | 钱怎么动？ | B1 锁在户内不流出 / B2 单次流出 / B3 周期流出 / B4 流入（收钱） / B5 户内搬（赎回→转出） |
| **C 风险形态** | 有什么风险要防？ | C1 卡片风险 / C2 身份风险（密码、设备） / C3 授权范围（代办、他人在场） / C4 无风险（纯查询） |

**A × B × C 组合出的事件是无穷的，但组合出来的「链路骨架」只有 7 种。**
这 7 种就叫 **L1–L7 原型**。新增一个生活事件时，不要新写链路，只要问一句「它属于哪条原型，参数是什么」。

> **这是今天的方法论核心，也是答辩要讲的一句话：**
> 我们不枚举场景，我们枚举**链路的形状**。7 条形状 × 参数化 = 覆盖绝大部分生活事件。

## 3. 七条原型详表

每条原型的「端到端」定义一样，缺一不可：
① 口语触发词 → ② 缺槽位追问 → ③ DAG 装配 → ④ 计划卡（含余额轨迹） → ⑤ 三色判定（取最严） → ⑥ 审计留痕 → ⑦ 失败可恢复（冻结必释放）。

| # | 原型 | DAG 骨架 | 参数化覆盖的生活事件 | 涉及动作 | 归属 |
|---|---|---|---|---|---|
| **L1** | 预算锁定型<br>（A2 · B1→B2→B1） | `funds.freeze(预算)` → `merchant.order(≤预算)` → `funds.release(余额)` | 生日订花、搬家买家电、开学采购、过节送礼、装修定金、宠物看病预留 | `funds.freeze` / `merchant.order` / `funds.release`（+`transfer.create`） | 尹辰（已落地生日） |
| **L2** | 定期出资型<br>（A3 · B3） | 签约/定日程 → 到期扣款 → 可查可停 | 房租、水电燃气、学费分期、给父母生活费、健身年卡、保险续费 | `subscription.sign` / `subscription.cancel` / `subscription.list` / `transfer.schedule` | 王昌泽 |
| **L3** | 出行保障型<br>（A4 · C1） | 临时收紧（降限额/锁卡）→ 期间消费 → 到日自动恢复 | 出国旅游、出差、住院失联、考试周、给孩子用副卡 | `card.set_limit` / `card.lock` / `card.unlock` / `account.transactions` | 林晓研 |
| **L4** | 大额凑集型<br>（A4 · B5→B2） | 查余额 → 赎回补缺口 → 一次性转出 | 还房贷、装修尾款、学费、给父母汇款、买车首付 | `account.balance` / `wealth.list` / `wealth.redeem` / `transfer.create` | 高靖雯 |
| **L5** | 失卡止损型<br>（A1 · C1+C2） | 锁卡 → 挂失 → 补虚拟卡 → 改密码 → 查近期交易 | 卡丢了、手机丢了、钱包被偷、疑似盗刷 | `card.lock` / `card.report_lost` / `card.apply_virtual` / `password.change` / `account.transactions` | 林晓研 |
| **L6** | 阶段盘点型<br>（A1 · C4→B3 收敛） | 账单回顾 → 砍订阅 → 调仓 | 年终整理、换工作、结婚前、毕业、搬家后 | `bills.yearly` / `bills.category_trend` / `bills.monthly` / `subscription.list` / `subscription.cancel` / `wealth.subscribe` | 徐思云 |
| **L7** | 分摊收款型<br>（A1 · B4） | 发起收款 → 确认到账 → 记账 | AA 聚餐、合租分摊、团购、班级活动费、婚宴份子 | `transfer.request_collection` / `account.transactions` / `bills.monthly` | 尹辰 |

**组合律**：原型可以串起来，这就是「覆盖大部分场景」的乘法效应。

| 组合 | 生活事件 |
|---|---|
| L6 → L4 | 年终盘点发现缺口 → 赎回凑钱还房贷 |
| L5 → L3 | 卡丢了补新卡 → 立刻给新卡设出行限额 |
| L2 → L6 | 签约一堆订阅 → 半年后盘点砍掉 |
| L1 → L7 | 生日聚餐先锁预算 → 群里 AA 收款回补 |

> 答辩时只讲 3 条组合就够了，不要贪多。

## 5. 逐人分工（通俗版）

### 5.1 王昌泽 · ⑤ 订阅 + 渠道 + **L2 定期出资**

**解决什么问题**
用户的固定支出（房租、给爸妈生活费、学费分期）现在只能每次手动转，忘了就逾期；演示现场断网/手机打不开就演不了。

**前端会改什么**
新增「定期出资」卡片：金额 + 周期（一次性/每月/每年）+ 首期日 + 收款方 + 「随时可停」开关；订阅列表加「下次扣款日」和「近 12 个月是否涨价」；PWA 断网时给明确提示而不是白屏。

**后端会改什么**
`subscription.sign` 支持周期模板；`transfer.schedule` 与订阅合流到同一张「定期承诺」视图，避免同一个"每月 1 号"出现两条；`scripts/reset_demo.py` 一键重置种子（连续重置 3 次结果一致）。

**agent 问答改进效果举例**

| 用户原话 | 现在 | 改后 |
|---|---|---|
| 「以后每个月 1 号给我妈转 2000」 | 可能只建一笔，或追问很多轮 | 一句话出 3 步计划卡「签约定期转账 2000/月/每月 1 日 → 首次 11-01 → 可随时停」，黄级，确认即执行 |
| 「我不想再交那个视频会员了」 | 要用户说全名 | 从订阅列表里定位到唯一一条，直接出「取消」确认卡 |
| 「这个月怎么被扣了三次会员费」 | 只报总额 | 给出 3 笔明细 + 涨价时点 + 一键取消入口 |

### 5.2 高靖雯 · ① 转账 + **L4 大额凑集**

**解决什么问题**
大额用钱（还房贷、装修尾款、给父母汇款）时，用户不知道活期够不够、要从理财赎回多少、来不来得及，得在三个页面之间来回算。

**前端会改什么**
新增「凑钱」卡片：目标金额 → 缺口 → 资金来源建议（活期 / 理财可用 / 赎回后到账日）→ 一张确认卡看全 2 步；转账确认卡上标出「赎回 T+1 到账，赶得上 11-05 扣款」这类时间风险。

**后端会改什么**
`wealth.redeem` + `transfer.create` 组成 DAG，赎回金额按缺口自动算；净效应按「赎回 − 转出」计算（避免把户内搬钱误判成大额流出）；转出 >1000 仍然是红，不因前面有赎回就降级。

**agent 问答改进效果举例**

| 用户原话 | 现在 | 改后 |
|---|---|---|
| 「下个月房贷 8000，我钱够吗」 | 只报活期余额 | 「活期 3200，理财可用 12000，需赎回 4800，T+1 到账，赶得上 11-05」+「现在赎回 / 到日子再赎」两个选项 |
| 「帮我把 8000 转到我房贷卡」 | 余额不足直接失败 | 自动提议先赎 4800，一张计划卡看全 2 步，红级 → 强验证 → 执行 |
| 「转 200 给张伟」（有两个张伟） | 可能猜一个 | 追问「是尾号 3721 的张伟，还是上个月转过的那位」 |

### 5.3 徐思云 · ③ 理财 + **L6 阶段盘点**

**解决什么问题**
用户一年到头不知道钱花哪了、哪些订阅在偷跑、自己该不该买某个风险等级的产品。

**前端会改什么**
年度/阶段盘点页：全年收支 + 类目 Top5 + 订阅年化总支出 + 「砍掉这 2 个每年省 1200」的一键取消；风险测评 3–5 题问卷 → 等级 → 适当性解释卡（为什么能买 / 为什么不能买）。

**后端会改什么**
`bills.yearly` + `subscription.list/cancel` + `wealth.subscribe` 组成 DAG；测评结果作为**可信事实**写入网关（模型不得自己编等级）；申购时做适当性匹配，不匹配 → 拒绝 + 给替代方案，不是"劝一劝就办"。

**agent 问答改进效果举例**

| 用户原话 | 现在 | 改后 |
|---|---|---|
| 「我这一年钱都花哪了」 | 给月度账单 | 年度卡（总额 / 类目 / 同比）+ 3 条可执行建议，其中 1 条带「取消」按钮 |
| 「我想买这个 R4 的」 | 直接下单 | 「您的风险等级 C2（稳健型），R4 超出适当性，不能买。相近的 R2 产品是…」→ 拒绝 + 替代 |
| 「我是不是花钱太多了」 | 泛泛安慰 | 拿数据说话：同比 +18%，超支集中在餐饮，并给「设个每月餐饮预算」的可执行动作 |

### 5.4 林晓研 · ② 账单 + ④ 卡片 + **L3 出行保障** + **L5 失卡止损**

> 两个原型共用同一套卡片动作，代码增量小，但**两条都要端到端**。

**解决什么问题**
卡片风险就两类高频事：**「出国/出差期间怕被盗刷」**和**「卡丢了、怀疑被盗刷，要 1 分钟内止损」**。这两件现在都得用户自己知道该按哪个按钮。

**前端会改什么**
- 出行保障卡：限额 + 起止日期 + 「到日自动恢复」；
- 失卡止损卡：四步进度条（锁卡 → 挂失 → 补虚拟卡 → 改密码），每步可单独执行或跳过，失败步骤标红但不阻塞后续；
- 异常交易卡：可疑交易打标 + 「顺手锁卡」按钮。

**后端会改什么**
`card.set_limit` / `card.lock` / `card.report_lost` / `card.apply_virtual` / `password.change` 组成 DAG，并且**部分失败要能回滚**（补虚拟卡失败，不能把卡永久锁死）；`account.transactions` 补异常识别（重复扣款、异地、深夜大额）。

**agent 问答改进效果举例**

| 用户原话 | 现在 | 改后 |
|---|---|---|
| 「我下周去日本，怕被盗刷」 | 用户得自己找限额页 | 「把境外单笔限额降到 500，回国 11-03 自动恢复。要现在设吗？」→ 红级（调额）→ 强验证 → 一张卡看全 |
| 「我卡好像丢了」 | 只锁卡，剩下的用户不知道 | 「先锁卡（已锁）→ 是否确认挂失（不可逆，红）→ 补一张虚拟卡 → 改密码」，四步自动排好，但每一步都停下来问 |
| 「这笔 899 我没买过」 | 只说"已记录" | 定位那一笔 + 「已标记可疑，建议同时锁卡」，一键接上 L5 |

**agent 问答改进效果举例**
