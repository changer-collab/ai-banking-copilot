## 2. 生活场景怎么归类：三个维度 → 七条原型

任何一件「要用银行办事的生活事件」，都能拆成三个正交问题：

| 维度 | 问题 | 取值 |
|---|---|---|
| **A 时间形态** | 这笔钱什么时候动？ | A1 一次性（现在） / A2 先备后花（锁一段时间） / A3 周期性（每月） / A4 到某天必须完成 |
| **B 资金形态** | 钱怎么动？ | B1 锁在户内不流出 / B2 单次流出 / B3 周期流出 / B4 流入（收钱） / B5 户内搬（赎回→转出） |
| **C 风险形态** | 有什么风险要防？ | C1 卡片风险 / C2 身份风险（密码、设备） / C3 授权范围（代办、他人在场） / C4 无风险（纯查询） |

A × B × C 组合出的事件是无穷的，但**链路骨架只有 7 种**，记作 L1–L7。
新增一个生活事件时，不要新写链路，只问一句「它属于哪条原型，参数是什么」。

> **答辩要讲的一句话：** 我们不枚举场景，我们枚举**链路的形状**。7 条形状 × 参数化 = 覆盖绝大部分生活事件。

**「端到端」的验收定义（7 项，缺一不算）**

① 口语触发词 → ② 缺槽位追问 → ③ DAG 装配 → ④ 计划卡（含余额轨迹） → ⑤ 三色判定（取最严） → ⑥ 审计留痕 → ⑦ 失败可恢复（冻结必释放）。

## 3. 为什么生活场景全部归尹辰

**因为生活链路天生是跨域的。**

| 原型 | 要同时碰几个域 | 如果分给组员会怎样 |
|---|---|---|
| L1 预算锁定 | ⑥ 跨场景 + `merchant.order` | 要改 `cross.py` + `catalog.py`，和组长撞 |
| L2 定期出资 | ⑤ 订阅 + ① 转账 | 王昌泽要改 `transfer.py`（高靖雯的文件） |
| L3 出行保障 | ④ 卡片 + ② 账单流水 | 林晓研要改 `account.transactions` 查询口径 |
| L4 大额凑集 | ③ 理财 + ① 转账 | 高靖雯要改 `wealth.py`（徐思云的文件） |
| L5 失卡止损 | ④ 卡片 + 身份 | 单域，但和 L3 抢同一批动作 |
| L6 阶段盘点 | ② 账单 + ⑤ 订阅 + ③ 理财 | 徐思云要改 3 个人的文件 |
| L7 分摊收款 | ① 转账 + ② 账单 | 高靖雯要改 `bills.py`（徐思云的文件） |

**所以分法反过来：按「域」分人，按「形状」分链路。**

- 组员 → **守住自己的域**：`scenarios/subscriptions.py` / `transfer.py` / `wealth.py` / `bills.py` / `cards.py` 的 `xxx_plan` 与 handler 稳定、可被调用、测试全绿。
- 尹辰 → **装配形状**：在 `scenarios/life_events.py` 登记七条原型，装配时**只调用**组员的 `xxx_plan`，不改他们的文件。

这样任何人都不需要为了一条链路去改别人的代码，也没有合并冲突。
